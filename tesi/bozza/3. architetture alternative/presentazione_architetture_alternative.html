Architetture Alternative di Verifica

Studio comparativo delle opzioni di isolamento e motivazioni tecniche di scarto

01 / 14
Opzione Esplorata Pregio / Vantaggio Principale Difetto Fatale (Fatal Flaw)
3.1 Shadow Bridge L2 Zero complessità SDN, solo primitive kernel native (FDB L2). No WAN: Container isolati da Internet (`apt`, DNS, chiamate HTTP esterne).
3.2 Dual NIC (`eth0`+`eth1`) Ripristina connettività WAN verso `incusbr0`. Rottura fedeltà topologica: Routing asimmetrico e drop da `rp_filter`.
3.3 PID Namespace Esecuzione in-place: zero clonazione di container o storage. Leaky & Distruttivo: Log e `/tmp` visibili, sniffing su `lo`, crash live dell'SLA.
3.4 Network Namespace Isolamento IP nativo sull'host senza stack SDN OVN. Bypass API Incus: Disallineamento orchestratore, contesa `rtnl_lock`, no cluster.
3.5 In-Memory + Mascheramento Esecuzione fileless volatile (`memfd_create` + `fexecve`). Security by Obscurity: Bypass con binari statici Go/Rust, visibile a eBPF.

Architettura Shadow Bridge L2

Switch L2 nel Kernel Linux (struct net_bridge)

Indirizzi IP Invariati tra i Cloni

04
Invisibilità L3 sull'Host

Poiché il bridge non ha IP, non espone socket né porte di ascolto ed è trasparente per lo stack di routing dell'host.

SEZIONE 3.1 • SHADOW BRIDGE L2 (2/2)

Shadow Bridge: Il Limite Fatale

Impossibilità di routing WAN e collisione delle tabelle FIB

03 / 14

1. Mancata Risoluzione ARP del Gateway

Fatal Flaw
01
Richiesta ARP senza Risposta

I container cercano il gateway 10.k.1.1 via ARP broadcast: nessuno risponde sull'interfaccia host non configurata.

02
Isolamento Totale da Internet

Comandi come apt update, risoluzione DNS esterna (1.1.1.1) o download di payload falliscono sistematicamente.

2. Collisione FIB nel Kernel Host

Routing Clash
03
Conflitto di Assegnazione IP

Assegnare 10.k.1.1 sia a br-team-k che al bridge shadow creerebbe due rotte identiche per 10.k.1.0/24.

04
Verdetto di Scarto

Adatta solo per sfide completamente offline; scartata per garantire supporto a exploit con dipendenze esterne.

Motivo di scarto: Assenza connettività WAN e conflitto FIB

SEZIONE 3.2 • DUAL NIC (2/2)

Dual NIC: Rottura Fedeltà & rp_filter

Routing asimmetrico, silent drop dei pacchetti e overhead di sistema

05 / 14

1. Violazione della Fedeltà Topologica

Topological Flaw
01
Ambiente Alterato

Il container in verifica ha 2 interfacce anziché 1: altera comandi come ip a, regole firewall locali e socket bind.

02
Routing Asimmetrico

I pacchetti di test entrano da eth0, ma la risposta viene instradata su eth1 perché default route.

2. Drop Silenzioso da rp_filter

Kernel Security
03
Reverse Path Filtering (rp_filter=1)

Il kernel Linux scarta i pacchetti asimmetrici considerandoli IP spoofing: le connessioni di verifica cadono misteriosamente.

04
Raddoppio Coppie veth

Raddoppia il numero di interfacce virtuali (da N a 2N), incrementando contesa e interrupt software nell'host.

Motivo di scarto: Routing asimmetrico e rottura della fedeltà

SEZIONE 3.3 • PID NAMESPACE (2/3)

PID Namespace: Canali di Fuga Informativa

Filesystem condiviso, inotify su /proc e network sniffing su loopback

07 / 14

Filesystem Condiviso

FS Leaks
📁
File Temporanei in /tmp

Script o exploit che creano artefatti temporanei lasciano tracce leggibili dal concorrente.

📜
Tracce nei File di Log

I servizi web o database loggano le richieste in /var/log: il concorrente può estrarre il payload.

Inotify & /proc Spying

pspy Vulnerable
👁️
Eventi Inotify del Kernel

Tool come pspy intercettano la creazione di directory in /proc rivelando comandi e argomenti.

🗂️
Mount Namespace Obbligatorio

Isolare solo il PID non basta: serve anche isolare il mount namespace per smontare /proc.

Sniffing su Loopback

Network Leaks
📡
tcpdump -i lo in Chiaro

Lo stack di rete resta identico: il partecipante può sniffare l'interfaccia lo o eth0.

🔍
Ispezione Socket con ss

Connessioni verso porte locali compaiono nelle tabelle di stato visibili all'utente.

Side-channel inevitabili in ambiente in-place condiviso

SEZIONE 3.4 • NETWORK NAMESPACE (2/2)

Network Namespace: Disallineamento Incus

Bypass dell'orchestratore, script manuali e contesa su rtnl_lock

10 / 14

1. Nessuna API Nativa in Incus

Orchestrator Bypass
01
Incus non Gestisce ip netns Arbitrari

Il motore Incus opera nel proprio namespace e non supporta l'aggancio diretto a bridge collocati in altri netns.

02
Manipolazione Manuale di veth

L'agente dovrebbe spostare le veth con ip link set dev ... netns, creando uno stato non tracciato dall'orchestratore.

2. Contesa Kernel & Mancanza di Scalabilità

Kernel Bottleneck
03
Contesa su rtnl_lock & Dangling Devices

Creazione e distruzione continua di netns causa contese sul lock globale di routing e rischio di leak di descrittori.

04
Inadatto a Cluster Multi-Nodo

I network namespace sono strettamente locali all'host, mentre OVN astrae switch logici distribuiti su tunnel Geneve.

Motivo di scarto: Disallineamento da Incus e complessità manutentiva

SEZIONE 3.5 • ESECUZIONE IN-MEMORY (2/3)

Esecuzione In-Memory: Fragilità Tecnica

Perché i trucchi di occultamento falliscono in ambienti reali

12 / 14

1. Bypass Immediato di LD_PRELOAD

User-Space Failure
01
Binari Statici & Go/Rust

I programmi statici o compilati in Go/Rust non usano glibc: effettuano syscall dirette, ignorando del tutto l'hook.

02
Partecipante con Privilegi Root

Il partecipante può rimuovere o modificare /etc/ld.so.preload in qualsiasi istante, disarmando il mascheramento.

2. Osservabilità a Livello Kernel

Kernel Tracing
03
eBPF & Syscall Auditing

Strumenti di tracing come eBPF (tracepoint:syscalls:sys_enter_execve) intercettano l'esecuzione in Ring 0.

04
/proc/[pid]/exe Revelatorio

Il descrittore /proc/[pid]/exe punta palesemente alla stringa /memfd:... (deleted) denunciando l'attività.

Fragilità dell'occultamento in presenza di binari statici ed eBPF

SEZIONE 3.5 • ESECUZIONE IN-MEMORY (3/3)

Il Fallimento della Security by Obscurity

Violazione dei principi di Saltzer e Schroeder e superiorità del modello CoW

13 / 14

I Limiti della "Sicurezza per Oscuramento"

Design Flaw
01
Nessuna Protezione della Rete

Anche se il binario è in RAM, le richieste HTTP dell'exploit viaggiano su rete e sono visibili a tcpdump.

02
Nessuna Protezione da Crash

L'ambiente è pur sempre di produzione: payload distruttivi mandano comunque in crash il servizio live.

03
Violazione Principi di Saltzer-Schroeder

La sicurezza deve basarsi su confini formali di isolamento (CoW, hypervisor, OVN), non su artifici di camuffamento.

Perché BlueAgent è Superiore

Formal Isolation
01
Isolamento Totale a Livello di Blocco

Clonazione ZFS Copy-on-Write in ~700 ms: indipendenza assoluta da memoria, file e processi della produzione.

02
Dark Sandbox SDN (OVN)

Datapath incapsulato su Geneve nel localhost: impossibile intercettare pacchetti tramite sniffing locale.

03
SLA Immutabile & Zero Rischio

Qualsiasi crash distruttivo si esaurisce nel clone effimero, preservando l'integrità del team.

Conclusione: L'isolamento formale supera l'occultamento in user-space
