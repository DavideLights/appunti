# Requisiti di Sistema e Requisiti Utente


---

## 1. Requisiti Utente (User Requirements)

Convenzione identificativa: **`UR-<CATEGORIA>-<ID>`**

### Categoria UR-ACC: Accesso, Connettività & User Experience
| Codice        | Titolo Requisito                            | Descrizione Operativa                                                                                                                                                                     | Ruolo Beneficiario |
| :------------ | :------------------------------------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------- |
| **UR-ACC-01** | Connessione VPN dedicata e sicura           | Il partecipante deve poter accedere in modo esclusivo, cifrato e diretto al proprio ambiente di gara tramite un **tunnel WireGuard** dedicato, utilizzando la **propria configurazione**. | Partecipante       |
| **UR-ACC-02** | Topologia di rete uniforme e deterministica | Ogni squadra deve disporre della medesima topologia interna (`10.k.1.0/24`) e degli stessi indirizzi IP statici (es. Server Web su `.2`, Database su `.3`).                               | Partecipante       |
| **UR-ACC-03** | Prestazioni I/O e latenza near-bare-metal   | Il traffico del concorrente sull'host, deve interagire con i container a velocità nativa di bus **RAM** sfruttando i bridge kernel L2                                                     | Partecipante       |

### Categoria UR-CHL: Definizione Challenge & IaC
| Codice        | Titolo Requisito                          | Descrizione Operativa                                                                                                                                                    | Ruolo Beneficiario |
| :------------ | :---------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------- |
| **UR-CHL-01** | Definizione dichiarativa via YAML (IaC)   | L'autore della sfida deve poter descrivere l'intera architettura della sfida tramite un manifesto **YAML**                                                               | Autore Sfida       |
| **UR-CHL-02** | Ambienti multi-container e stateful       | La piattaforma deve supportare scenari complessi multi-tier basati su **container di sistema**.                                                                          | Autore Sfida       |
| **UR-CHL-03** | Quote e vincoli di risorse (Cgroups v2)   | L'autore deve poter definire quote massime perentorie di CPU e memoria RAM per evitare la starvation dell'host.                                                          | Autore Sfida       |
| **UR-CHL-04** | Controlli di prontezza (Readiness Checks) | L'autore deve poter dichiarare sequenze di **boot check** (es. socket listening, ping database) eseguite prima di avviare il processo di verifica sui controller clonati | Autore Sfida       |

### Categoria UR-VER: Verifica, Valutazione & Integrità
| Codice        | Titolo Requisito                      | Descrizione Operativa                                                                                                                                                                                                                  | Ruolo Beneficiario           |
| :------------ | :------------------------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------- |
| **UR-VER-01** | Verifica non distruttiva ed oscurata. | L'esecuzione degli exploit di verifica o dei controlli di patch non *deve alterare lo stato (**oscurata**) né mandare in crash l'ambiente di produzione vivo del team (**non distruttiva**)*, proteggendone la **percentuale di SLA**. | Partecipante / Organizzatore |
| **UR-VER-02** | Protezione da Side-Channel Leaks      | I payload di exploit, gli script di validazione e le flag non devono essere intercettabili dai partecipanti (es. tramite packet sniffing `tcpdump` sul bridge live o ispezione log/processi).                                          | Organizzatore / Autore       |
| **UR-VER-03** | Dual-Mode Verification                | L'autore deve poter scegliere **dove eseguire il comando di verifica**: su un container di verifica ad-hoc, oppure direttamente sui container della sfida                                                                              | Autore Sfida                 |
| **UR-VER-04** | Velocita della verifica               | La piattaforma deve calcolare e ritornare l'esito della verifica in pochi secondi, sfruttando gli snapshot di **ZFS**.                                                                                                                 | Partecipante / Organizzatore |

### Categoria UR-ORG: Amministrazione, Orchestrazione & API
| Codice        | Titolo Requisito                          | Descrizione Operativa                                                                              | Ruolo Beneficiario                   |
| :------------ | :---------------------------------------- | :------------------------------------------------------------------------------------------------- | :----------------------------------- |
| **UR-ORG-01** | Control Plane REST API programmabile      | Tutte le funzionalità devono essere richiamabili via API HTTP mediante un token di autenticazione. | Organizzatore / CTFd                 |
| **UR-ORG-03** | Bonifica e auto-guarigione (Self-Healing) | I container e le reti create per la verifica vengono distrutti se creati da piu di **90 secondi.** | Organizzatore / Admin / Partecipante |

## 2. Requisiti di Sistema (System Requirements)

Convenzione identificativa: **`SR-<CATEGORIA>-<ID>`**

### Categoria SR-HST: Host & Piattaforma di Esecuzione
| Codice        | Componente        | Descrizione Tecnica                                                                                        | Riferimento Codice                                         |
| :------------ | :---------------- | :--------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------- |
| **SR-HST-01** | Sistema Operativo | L'host esegue Debian 13 (Trixie) con IP forwarding abilitato ed `nftables` supportato.                     | `scripts/host_setup.sh`                                    |
| **SR-HST-02** | Storage Pool CoW  | L'host deve fornire uno storage pool `blueagent-zfs`.                                                      | `src/blueagent/config.py`, `src/blueagent/engine/incus.py` |
| **SR-HST-03** | Demoni SDN Host   | L'host ha configurato Open vSwitch e OVN (`ovs-vswitchd`, `ovsdb-server`, `ovn-northd`, `ovn-controller`). | `scripts/host_setup.sh`                                    |


---

### Categoria SR-ENG: Motore di Containerizzazione & I/O
| Codice        | Componente                    | Descrizione Tecnica                                                                                                                 | Riferimento Codice              |
| :------------ | :---------------------------- | :---------------------------------------------------------------------------------------------------------------------------------- | :------------------------------ |
| **SR-ENG-01** | Interfaccia Astratta Engine   | Implementazione dell'interfaccia astratta `ContainerEngine`.                                                                        | `src/blueagent/engine/base.py`  |
| **SR-ENG-02** | Client Asincrono UDS          | `IncusEngine` comunica con l'istanza di Incus via Unix Domain Socket .                                                              | `src/blueagent/engine/incus.py` |
| **SR-ENG-03** | Sincronizzazione Long-Polling | La sincronizzazione delle operazioni asincrone di Incus deve avvenire invocando l'endpoint `/1.0/operations/{uuid}/wait?timeout=N`. | `src/blueagent/engine/incus.py` |
| **SR-ENG-04** | Clonazione Snapshot CoW       | Implementazione del metodo `clone_instance` basato su copia a livello di snapshot.                                                  | `src/blueagent/engine/incus.py` |
| **SR-ENG-05** | Isolamento Cgroups v2         | Applicazione delle quote hardware `limits.cpu` e `limits.memory` sulle istanze Incus.                                               | `src/blueagent/engine/incus.py` |

### Categoria SR-NET: Rete Ibrida, Routing & Traffico
| Codice        | Componente                             | Descrizione Tecnica                                                                                                                     | Riferimento Codice                                                          |
| :------------ | :------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------- |
| **SR-NET-01** | Tunnel WireGuard L3 Multi-Member       | Per ciascun team $k$, creazione dell'interfaccia `wg-k` su subnet `10.k.0.1/24` (porta UDP `51820 + k`)                                 | `src/blueagent/network/wireguard.py`, `src/blueagent/network/addressing.py` |
| **SR-NET-02** | Linux Bridge L2 Live                   | Per ciascun team $k$, allocazione di un bridge kernel `br-team-k` con IP gateway `10.k.1.1/24`, e di un profilo Incus `team-k-profile`. | `src/blueagent/network/host_net.py`                                         |
| **SR-NET-03** | Overlay OVN Dark Sandbox               | Per ogni sessione di verifica, creazione di una rete SDN OVN effimera (`verify-k`) isolata dall'ambiente di produzione.                 | `src/blueagent/verifier/ovn.py`                                             |
| **SR-NET-04** | Fedeltà Topologica in fase di verifica | Coesistenza simultanea della medesima subnet (`10.k.1.0/24`), sia in rete di produzione che in rete di verifica per il team `k`.        | `src/blueagent/verifier/ovn.py`                                             |
| **SR-NET-05** | TCP MSS Clamping                       | Applicazione di regole nftables  per azzerare il fenomeno dell'MTU Blackhole tra a causa di WireGuard e Genevee                         | `src/blueagent/network/host_net.py`                                         |
| **SR-NET-06** | NAT Masquerade                         | Configurazione del mascheramento postrouting nftables per la rete `10.0.0.0/8` verso l'uscita dall'host.                                | `src/blueagent/network/host_net.py`                                         |
