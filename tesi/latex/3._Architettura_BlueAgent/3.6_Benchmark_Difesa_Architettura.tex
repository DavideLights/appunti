\section{Benchmark e Difesa
dell\textquotesingle Architettura}\label{benchmark-e-difesa-dellarchitettura}

Per concludere l\textquotesingle esposizione
dell\textquotesingle architettura di BlueAgent, vengono motivate le
principali scelte infrastrutturali e di codice rimaste aperte,
difendendo la validità del progetto rispetto ai requisiti di un Cyber
Range orientato al patch management.

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsection{Scelte di Piattaforma e
Infrastruttura}\label{scelte-di-piattaforma-e-infrastruttura}

\begin{itemize}
\item
  \textbf{Perché Debian 13 (Trixie)?}

  \begin{itemize}
  \tightlist
  \item
    \emph{Kernel moderno (6.x+):} Necessario per il supporto nativo a
    WireGuard e per le funzionalità avanzate di
    \passthrough{\lstinline!nftables!} (concatenazione di interfacce e
    set compositi \passthrough{\lstinline!@team\_links!} con
    intervalli).
  \item
    \emph{Pacchetti nativi \passthrough{\lstinline!.deb!}:} Distribuisce
    Incus, Open vSwitch e OVN come pacchetti di sistema standard,
    evitando layer di virtualizzazione invasivi o i pacchetti
    \passthrough{\lstinline!snap!} (tipici di Ubuntu) che complicano
    l\textquotesingle accesso ai socket UDS dell\textquotesingle host e
    isolano i mount namespace.
  \end{itemize}
\item
  \textbf{Perché ZFS?}

  \begin{itemize}
  \tightlist
  \item
    \emph{Clonazione istantanea CoW:} Consente di clonare interi
    container a livello di blocchi in circa 100 ms tramite Copy-on-Write
    (\passthrough{\lstinline!POST /1.0/instances!} copy), senza
    duplicazione fisica iniziale dei dati su disco.
  \item
    \emph{Footprint su disco minimo:} I blocchi aggiuntivi vengono
    scritti solo se modificati durante la verifica, permettendo repliche
    frequenti anche sotto carico senza saturare lo storage.
  \end{itemize}
\item
  \textbf{Perché Incus?}

  \begin{itemize}
  \tightlist
  \item
    \emph{System Container vs Application Container:} A differenza di
    Docker, pensato per singoli processi, Incus fornisce veri container
    di sistema con un init system completo
    (\passthrough{\lstinline!systemd!} o
    \passthrough{\lstinline!OpenRC!}). I concorrenti possono operare
    realisticamente come amministratori di sistema (installare pacchetti
    con \passthrough{\lstinline!apt!}, modificare configurazioni in
    \passthrough{\lstinline!/etc!}, riavviare demoni).
  \item
    \emph{Efficienza rispetto alle VM (KVM):} Condividendo il kernel
    dell\textquotesingle host, un container occupa pochi megabyte di RAM
    (contro i gigabyte preallocati di una VM) e si avvia in frazioni di
    secondo.
  \item
    \emph{Integrazione nativa:} Supporta nativamente sia i pool di
    storage ZFS sia i driver di rete OVN tramite API REST su socket Unix
    locale.
  \end{itemize}
\end{itemize}

\subsection{Scelte di Design Software e
Codice}\label{scelte-di-design-software-e-codice}

\begin{itemize}
\item
  \textbf{Validità delle API REST:}

  \begin{itemize}
  \tightlist
  \item
    \emph{Disaccoppiamento tra frontend e backend:} Il CTF Manager (es.
    CTFd) può risiedere su un server web leggero o in cloud, mentre
    BlueAgent opera direttamente sull\textquotesingle host fisico
    bare-metal dotato di Linux, ZFS e Incus.
  \item
    \emph{Interoperabilità e standard aperto:}
    L\textquotesingle adozione di HTTP/JSON autenticato con Bearer token
    permette a qualsiasi piattaforma, script di benchmark o interfaccia
    CLI di interagire con il Cyber Range senza dipendere da SDK
    proprietari.
  \item
    \emph{Mappatura naturale delle risorse:} Operazioni di creazione,
    consultazione di telemetria e distruzione di macchine e team
    corrispondono in modo diretto e deterministico ai metodi HTTP
    standard (\passthrough{\lstinline!POST!},
    \passthrough{\lstinline!GET!}, \passthrough{\lstinline!DELETE!}).
  \end{itemize}
\item
  \textbf{Perché SQLite (con WAL mode)?}

  \begin{itemize}
  \tightlist
  \item
    \emph{Zero overhead di gestione:} Elimina la complessità di dover
    installare, configurare e manutenere un demone database esterno
    (come PostgreSQL o MySQL). L\textquotesingle intero stato risiede su
    un singolo file locale.
  \item
    \emph{Concorrenza asincrona:} La modalità \textbf{WAL}
    (\emph{Write-Ahead Logging}) consente letture concorrenti non
    bloccanti da parte dei task asincroni durante le operazioni di
    scrittura, garantendo ottime prestazioni per il carico di lavoro di
    un singolo host.
  \end{itemize}
\end{itemize}

\subsection{Difesa
dell\textquotesingle Architettura}\label{difesa-dellarchitettura}

La bontà delle scelte architetturali di BlueAgent si difende su due
argomenti principali:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Invisibilità dell\textquotesingle Oracolo e Tutela dello SLA
  (Zero-Leakage):} Nelle gare di difesa i partecipanti possiedono
  privilegi di \passthrough{\lstinline!root!} sulla macchina target per
  applicare le patch. Se i test di verifica venissero eseguiti
  direttamente sull\textquotesingle ambiente di gioco, i partecipanti
  potrebbero intercettare il payload dell\textquotesingle oracolo
  tramite \passthrough{\lstinline!tcpdump!} o
  \passthrough{\lstinline!pspy!}, scoprendo la vulnerabilità e la
  soluzione. Inoltre, exploit distruttivi manderebbero in crash i
  servizi live, penalizzando ingiustamente lo SLA del team. La
  clonazione ZFS CoW in una sandbox OVN garantisce verifiche totalmente
  isolate, senza leak di informazioni né disservizi
  sull\textquotesingle ambiente di produzione.
\item
  \textbf{Efficienza di Scala e Densità:} Soluzioni basate su macchine
  virtuali complete richiedono ingenti risorse hardware (CPU e RAM
  dedicate), rendendo proibitivo ospitare decine di team su un singolo
  server. All\textquotesingle opposto, soluzioni leggere come
  kCTF/NSJail impediscono ai partecipanti di modificare il sistema
  operativo o persistere modifiche a livello di pacchetti. BlueAgent
  offre il punto di equilibrio ideale: pieno realismo sistemistico per i
  concorrenti e massima densità ed efficienza per
  l\textquotesingle infrastruttura.
\end{enumerate}

\subsection{Critica e Limiti
Architetturali}\label{critica-e-limiti-architetturali}

Nonostante i vantaggi, l\textquotesingle architettura presenta
compromessi e vincoli strutturali:

\begin{itemize}
\tightlist
\item
  \textbf{UDP Path MTU Blackhole:} La combinazione di tunnel WireGuard
  (\(\text{MTU } 1420\)) e Geneve OVN (\(\text{MTU } 1442\),
  all\textquotesingle interno della \textbf{rete di verifica}) impone
  riduzioni di MTU. Mentre il TCP beneficia del MSS clamping via
  \passthrough{\lstinline!nftables!}, i pacchetti UDP di grandi
  dimensioni con flag \emph{Don\textquotesingle t Fragment}, potrebbero
  essere scartati dal kernel.
\item
  \textbf{Limite scalabilità a 254 team:}
  L\textquotesingle indirizzamento deterministico
  \passthrough{\lstinline!10.k.x.x!} vincola \(k\) a un singolo byte
  (\(0 \le k \le 254\)), quindi ad un massimo di \(\text{255}\) team.
\item
  \textbf{Concorrenza e blocco multi-nodo:} Il meccanismo
  \passthrough{\lstinline!TwoTierLock!}
  (\passthrough{\lstinline!asyncio.Lock!} combinato con
  \passthrough{\lstinline!flock!}) è confinato al singolo nodo. Per
  scalare l\textquotesingle architettura su più nodi bisogna introdurre
  l\textquotesingle uso di un gestore di lock distribuito come Redis.
\end{itemize}
