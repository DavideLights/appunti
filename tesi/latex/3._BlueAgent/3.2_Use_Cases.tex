\section{Use Cases per CTF Manager}\label{use-cases-per-ctf-manager}

Sono elencati di seguito gli Use Case per il CTF Manager, arricchito con
alcuni dettagli implementativi per comprendere al meglio l'architettura
del software.

Di seguito è riportato un breve glossario:

\begin{quote}
\passthrough{\lstinline!br-team-k!}: è il bridge di rete che fornisce
una rete locale per i container del team \(k\). Ogni
\passthrough{\lstinline!br-team-k!} è una LAN separata dagli altri
\passthrough{\lstinline!br-team-k!}.
\end{quote}

\begin{quote}
\passthrough{\lstinline!wg-k!}: è l'interfaccia WireGuard che offre la
connettività VPN per il team \(k\) verso
\passthrough{\lstinline!br-team-k!}.
\end{quote}

\begin{quote}
\passthrough{\lstinline!eth0!}: in questo documento, spesso identifica
il nome dell'interfaccia che fornisce la connettività alla LAN per un
container.
\end{quote}

\begin{quote}
\passthrough{\lstinline!verify-k!}: è lo switch logico (gestito tramite
SDN) utilizzato per implementare la rete di verifica per il team \(k\).
Questa rete è completamente scollegata da
\passthrough{\lstinline!br-team-k!} e da \passthrough{\lstinline!wg-k!}.
\end{quote}

\begin{quote}
\passthrough{\lstinline!database!}: è il database SQL, usato da
BlueAgent per tenere traccia delle risorse allocate.
\end{quote}

\subsection{\texorpdfstring{\texttt{UC-01}: Deploy dell'infrastruttura
di rete per il team
\(k\)}{UC-01: Deploy dell'infrastruttura di rete per il team k}}\label{uc-01-deploy-dellinfrastruttura-di-rete-per-il-team-k}

\begin{itemize}
\tightlist
\item
  \textbf{Attore}: CTF Manager
\item
  \textbf{Obiettivo}: Effettuare il deploy delle interfacce di rete
  necessarie al team \(k\) per eseguire i container e consentire
  l'accesso VPN ai partecipanti.
\item
  \textbf{Precondizione}: BlueAgent è attivo ed è raggiungibile via API
  REST.
\end{itemize}

Flusso delle azioni:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Il CTF Manager invia la richiesta
  \passthrough{\lstinline!PUT /teams/\{team\_k\}!}, specificando
  l'identificativo \(k\) nel path ed il relativo nome nel payload.
\item
  BlueAgent verifica se l'infrastruttura per il team \(k\) esiste già:

  \begin{enumerate}
  \def\labelenumii{\arabic{enumii}.}
  \tightlist
  \item
    Se il team è già registrato, ne sincronizza la configurazione e
    risponde \passthrough{\lstinline!HTTP 200 OK!}.
  \item
    Altrimenti, l'infrastruttura di rete viene creata da zero:

    \begin{enumerate}
    \def\labelenumiii{\arabic{enumiii}.}
    \tightlist
    \item
      Viene creato il bridge \passthrough{\lstinline!br-team-k!} per il
      team \(k\) con IP per il gateway
      \passthrough{\lstinline!10.k.1.1/24!}.
    \item
      Viene creata l'interfaccia WireGuard
      \passthrough{\lstinline!wg-k!} per il team \(k\). La porta UDP è
      \passthrough{\lstinline!51820+k!}, l'IP per il gateway è
      \passthrough{\lstinline!10.k.0.1/24!}.
    \item
      Viene registrato il team all'interno del database.
    \item
      BlueAgent risponde con stato
      \passthrough{\lstinline!HTTP 201 Created!} confermando l'avvenuta
      creazione.
    \end{enumerate}
  \end{enumerate}
\end{enumerate}

Se avviene un errore irrimediabile durante la creazione, il bridge e
l'interfaccia WireGuard create vengono rilasciate.

\subsection{\texorpdfstring{\texttt{UC-02}: Deploy della challenge per
il team
\(k\)}{UC-02: Deploy della challenge per il team k}}\label{uc-02-deploy-della-challenge-per-il-team-k}

\begin{itemize}
\tightlist
\item
  \textbf{Attore}: CTF Manager
\item
  \textbf{Obiettivo}: Effettuare il deploy dei container necessari alla
  challenge da allestire per il team \(k\) richiedente.
\item
  \textbf{Precondizione}: \passthrough{\lstinline!UC-01!},
  \passthrough{\lstinline!UC-05!}. È stato eseguito con successo il
  deploy dell'infrastruttura di rete per il team \(k\) e le immagini dei
  container richieste sono presenti nel catalogo in stato
  \passthrough{\lstinline!ready!}.
\end{itemize}

Flusso delle azioni:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Il CTF Manager invia la richiesta
  \passthrough{\lstinline!POST /teams/\{team\_k\}/machines!}
  specificando la configurazione della challenge.
\item
  BlueAgent valida le precondizioni.
\item
  Per ogni container specificato nella configurazione:

  \begin{enumerate}
  \def\labelenumii{\arabic{enumii}.}
  \tightlist
  \item
    Crea l'istanza del container.
  \item
    Collega l'interfaccia virtuale \passthrough{\lstinline!eth0!}
    dell'istanza al bridge del team \passthrough{\lstinline!br-team-k!}.
  \item
    Inietta nel filesystem dell'istanza la configurazione di rete
    statica.
  \item
    Avvia l'istanza del container ed applica l'indirizzo IP statico.
  \item
    Registra il container nel database.
  \end{enumerate}
\item
  BlueAgent restituisce la risposta con stato
  \passthrough{\lstinline!HTTP 201 Created!}.
\end{enumerate}

Se si verifica un errore durante l'avvio, BlueAgent arresta ed elimina
tutte le istanze e le risorse create fino a quel momento per la
challenge e risponde con un errore.

\subsection{\texorpdfstring{\texttt{UC-03}: Verifica della challenge per
il team
\(k\)}{UC-03: Verifica della challenge per il team k}}\label{uc-03-verifica-della-challenge-per-il-team-k}

\begin{itemize}
\tightlist
\item
  \textbf{Attore}: CTF Manager
\item
  \textbf{Obiettivo}: Verificare l'integrità dei servizi e l'efficacia
  delle patch applicate dal team mediante l'esecuzione dei comandi
  specificati nella configurazione della challenge.
\item
  \textbf{Precondizioni}: \passthrough{\lstinline!UC-02!}. I container
  relativi alla challenge specificata per il team \(k\) sono attivi.
\end{itemize}

Flusso delle azioni:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Il CTF Manager invia la richiesta
  \passthrough{\lstinline!POST /teams/\{team\_k\}/verificator!}
  trasmettendo la configurazione della challenge da verificare.
\item
  Se una verifica per lo stesso team è già in corso, BlueAgent risponde
  con \passthrough{\lstinline!HTTP 409 Conflict!}.
\item
  Altrimenti, BlueAgent predispone l'ambiente di verifica:

  \begin{enumerate}
  \def\labelenumii{\arabic{enumii}.}
  \tightlist
  \item
    Crea uno switch logico OVN denominato
    \passthrough{\lstinline!verify-k!}.
  \item
    Esegue la clonazione CoW di tutti i container della challenge del
    team \(k\).
  \item
    Riconfigura l'interfaccia \passthrough{\lstinline!eth0!} dei cloni
    agganciandola allo switch OVN di verifica.
  \item
    Avvia i cloni sandbox e configura al loro interno lo stesso
    indirizzo IP statico di produzione
    (\passthrough{\lstinline!10.k.1.\{ip\_suffix\}/24!}).
  \item
    Se specificato nella configurazione, avvia un container di verifica
    runner.
  \end{enumerate}
\item
  Esecuzione dei controlli di readiness: viene eseguito un ciclo di
  tentativi finché il comando non ha successo, oppure fino allo scadere
  del timeout.
\item
  Esegue i comandi di verifica all'interno dei container clonati o dal
  container runner.
\item
  Dealloca le risorse sandbox create per il controllo.
\item
  BlueAgent risponde con stato \passthrough{\lstinline!HTTP 200 OK!}
  comunicando l'esito della verifica.
\end{enumerate}

Se si verifica un errore, oppure i comandi di readiness non hanno
successo, allora le risorse utilizzate vengono rilasciate e viene
comunicato l'errore.

\subsection{\texorpdfstring{\texttt{UC-04}: Dismissione e rilascio di
una challenge per il team
\(k\)}{UC-04: Dismissione e rilascio di una challenge per il team k}}\label{uc-04-dismissione-e-rilascio-di-una-challenge-per-il-team-k}

\begin{itemize}
\tightlist
\item
  \textbf{Attore}: CTF Manager
\item
  \textbf{Obiettivo}: Rimuovere tutti i container associati a una
  determinata challenge per il team \(k\).
\item
  \textbf{Precondizioni}: I container associati alla challenge
  specificata sono attivi per il team \(k\).
\end{itemize}

Flusso delle azioni:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Il CTF Manager invia la richiesta
  \passthrough{\lstinline!DELETE /teams/\{team\_k\}/machines!}
  specificando nel payload la configurazione della challenge.
\item
  Per ciascun container specificato nella configurazione della
  challenge:

  \begin{enumerate}
  \def\labelenumii{\arabic{enumii}.}
  \tightlist
  \item
    Arresta l'istanza.
  \item
    Elimina l'istanza.
  \item
    Cancella il record del container dal database.
  \end{enumerate}
\item
  BlueAgent risponde con stato
  \passthrough{\lstinline!HTTP 204 No Content!}.
\end{enumerate}

In caso di problemi durante il teardown di uno o più container,
BlueAgent restituisce un errore HTTP con i dettagli dell'anomalia.

\subsection{\texorpdfstring{\texttt{UC-05}: Compilazione e Import di
un'immagine per
container}{UC-05: Compilazione e Import di un'immagine per container}}\label{uc-05-compilazione-e-import-di-unimmagine-per-container}

\begin{itemize}
\tightlist
\item
  \textbf{Attore}: CTF Manager
\item
  \textbf{Obiettivo}: Inviare la specifica di un'immagine in formato
  YAML ed avviare la compilazione e l'importazione nel catalogo delle
  immagini.
\item
  \textbf{Precondizione}: BlueAgent è attivo.
\end{itemize}

Flusso delle azioni:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Il CTF Manager invia la richiesta
  \passthrough{\lstinline!PUT /images/\{alias\}!} inviando una form
  multipart con il file di definizione YAML o l'archivio di contesto.
\item
  BlueAgent valida la specifica YAML e ne calcola l'hash crittografico.
\item
  BlueAgent verifica lo stato dell'immagine nel database:

  \begin{enumerate}
  \def\labelenumii{\arabic{enumii}.}
  \tightlist
  \item
    Se l'immagine con lo stesso hash esiste già ed è in stato
    \passthrough{\lstinline!ready!}, risponde immediatamente con
    \passthrough{\lstinline!HTTP 200 OK!}.
  \item
    Altrimenti, registra un nuovo record nel database in stato
    \passthrough{\lstinline!building!}.
  \end{enumerate}
\item
  BlueAgent avvia la compilazione tramite un worker asincrono:

  \begin{enumerate}
  \def\labelenumii{\arabic{enumii}.}
  \tightlist
  \item
    Esegue Distrobuilder ed importa l'immagine generata nel catalogo dei
    container Incus.
  \item
    Assegna l'alias all'immagine importata e aggiorna il record a
    \passthrough{\lstinline!ready!} nel database.
  \end{enumerate}
\item
  BlueAgent restituisce immediatamente al CTF Manager lo stato
  \passthrough{\lstinline!HTTP 202 Accepted!} se la compilazione è stata
  avviata.
\end{enumerate}

\subsection{\texorpdfstring{\texttt{UC-06}: Registrazione e
configurazione WireGuard per un membro del team
\(k\)}{UC-06: Registrazione e configurazione WireGuard per un membro del team k}}\label{uc-06-registrazione-e-configurazione-wireguard-per-un-membro-del-team-k}

\begin{itemize}
\tightlist
\item
  \textbf{Attore}: CTF Manager
\item
  \textbf{Obiettivo}: Registrare un giocatore come membro del team
  \(k\), allocare un indirizzo IP nella subnet VPN, generare le chiavi
  crittografiche WireGuard e restituire il file di configurazione
  \passthrough{\lstinline!.conf!}.
\item
  \textbf{Precondizioni}: \passthrough{\lstinline!UC-01!}.
  L'infrastruttura di rete per il team \(k\) è attiva sul sistema.
\end{itemize}

Flusso delle azioni:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Il CTF Manager invia la richiesta
  \passthrough{\lstinline!PUT /teams/\{team\_k\}/members/\{user\_id\}!}
  fornendo il nome dell'utente ed opzionalmente la chiave pubblica
  WireGuard.
\item
  BlueAgent verifica se il team \(k\) è registrato; se assente, risponde
  con \passthrough{\lstinline!HTTP 404 Not Found!}.
\item
  BlueAgent verifica se il membro è già registrato nel database per il
  team \(k\):

  \begin{enumerate}
  \def\labelenumii{\arabic{enumii}.}
  \tightlist
  \item
    Se il membro esiste già, BlueAgent aggiorna la configurazione
    rispondendo con \passthrough{\lstinline!HTTP 200 OK!}.
  \item
    Se il membro è nuovo:

    \begin{enumerate}
    \def\labelenumiii{\arabic{enumiii}.}
    \tightlist
    \item
      Alloca un indirizzo IP VPN libero per il team
      (\passthrough{\lstinline!10.k.0.2!} -
      \passthrough{\lstinline!10.k.0.254!}). Se lo spazio degli
      indirizzi è esaurito, risponde con
      \passthrough{\lstinline!HTTP 409 Conflict!}.
    \item
      Se non fornita, genera una nuova coppia di chiavi asimmetriche.
    \item
      Registra il nuovo peer sull'interfaccia
      \passthrough{\lstinline!wg-k!}.
    \item
      Salva il record del membro nel database.
    \end{enumerate}
  \end{enumerate}
\item
  BlueAgent risponde con stato
  \passthrough{\lstinline!HTTP 201 Created!} restituendo i dati del
  membro e la configurazione WireGuard generata.
\end{enumerate}
