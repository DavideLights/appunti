\section{CR Alternativi: kCTF}\label{cr-alternativi-kctf}

kCTF\footnote{\label{fn:ref_2}Google Security Team, \emph{kCTF: Kubernetes-based CTF
  infrastructure}, https://google.github.io/kctf/} è una piattaforma
sviluppata da Google basata su \emph{Kubernetes} e \emph{nsjail}.

\begin{quote}
\emph{Kubernetes}: è un sistema open source per automatizzare il deploy,
scalare e gestire applicazioni containerizzate.\footnote{\label{fn:ref_3}The Linux
  Foundation, \emph{Kubernetes Documentation},
  https://kubernetes.io/docs/}
\end{quote}

\begin{quote}
\emph{NSJail} NameSpace Jail. È un tool Linux per isolare i processi
utilizzando varie feature del kernel come: namespaces, resource limits e
seccomp-bpf syscall filters. L'obiettivo di NSJail è quello di creare un
ambiente sicuro e isolato per eseguire le applicazioni. \footnote{\label{fn:ref_4}Google,
  \emph{NsJail: A light-weight process isolation tool},
  https://github.com/google/nsjail/}
\end{quote}

Facendo riferimento alla Figura \ref{fig:kctf-architecture},
l'architettura di kCTF prevede:

\begin{itemize}
\tightlist
\item
  Un \textbf{cluster}, che contiene un insieme di challenge
\item
  Dei \textbf{deployment}, ognuno contiene due container (o meglio, un
  Pod che istanzia 2 container):

  \begin{itemize}
  \tightlist
  \item
    un container \passthrough{\lstinline!healthcheck!}: usato per
    determinare lo stato di salute dei servizi
  \item
    un container \passthrough{\lstinline!challenge!}: contiene i servizi
    su cui lavora lo sfidante.
  \end{itemize}
\end{itemize}

\begin{quote}
\textbf{Pod}: in Kubernetes, è la più piccola unità che Kubernetes può
eseguire. Un Pod, rappresenta uno o più container in esecuzione su un
singolo nodo.\footnote{\label{fn:ref_5}The Kubernetes Authors, \emph{Workload
  Management: Pods and Deployments},
  https://kubernetes.io/docs/concepts/workloads/}
\end{quote}

\begin{quote}
\textbf{Deployment}: in Kubernetes, un deployment è un template che
specifica come creare i container. I template guidano la creazione di
\textbf{Pods} e la gestione sicura del ciclo di vita di un Pod, in
particolare la gestione dei ReplicaSet.\footref{fn:ref_5}
\end{quote}

NSJail viene avviato su ogni container
\passthrough{\lstinline!challenge!}, ed è configurato per ascoltare su
una porta TCP nota. Ad ogni connessione TCP in arrivo, NSJail esegue un
fork restituendo allo sfidante un ambiente separato (rispetto agli altri
sfidanti) su cui lavorare. L'obiettivo di questa architettura è di poter
riutilizzare lo stesso container per più sfidanti.

L'isolamento fornito da NSJail, si ottiene combinando varie tecniche:

\begin{itemize}
\tightlist
\item
  Creazione di nuovi namespace: l'ambiente fornito, esegue su un nuovo
  namespace, separando logicamente le risorse accessibili.
\item
  Filtraggio delle chiamate di sistema tramite
  \passthrough{\lstinline!seccomp-bpf!}: questo sottosistema permette di
  uccidere i processi nell'ambiente se vengono eseguite chiamate di
  sistema vietate.
\item
  Accounting e limitazione delle risorse con
  \passthrough{\lstinline!cgroup!}: questo sottosistema permette di
  monitorare e limitare le risorse utilizzabili nel nuovo ambiente.
\end{itemize}

NsJail può essere configurato in modo che ogni ambiente isolato, abbia a
disposizione un filesystem temporaneo che risiede in RAM, mentre il
filesystem originale è accessibile dall'ambiente sandbox in sola
lettura. Questa configurazione è necessaria poiché altrimenti gli
sfidanti modificherebbero tutti lo stesso filesystem.

Un'altra configurazione di NSJail è la seguente, ideale per le challenge
di tipo \passthrough{\lstinline!pwn!} (trovare e sfruttare vulnerabilità
in file binari):

\begin{lstlisting}
[...]
mount: [
  {
    src: "/chroot"
    dst: "/"
    is_bind: true
  },
  {
    dst: "/tmp"
    fstype: "tmpfs"
    rw: true
  },
  {
    dst: "/proc"
    fstype: "proc"
    rw: true
  },
  {
    src: "/etc/resolv.conf"
    dst: "/etc/resolv.conf"
    is_bind: true
  }
]
\end{lstlisting}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  La cartella \passthrough{\lstinline!/chroot!} che risiede nel
  container, diventa la radice nel nuovo ambiente.
\item
  Viene creato un nuovo \passthrough{\lstinline!tmpfs!}, in
  \passthrough{\lstinline!/tmp!}
\item
  Viene importata la configurazione DNS da
  \passthrough{\lstinline!/etc/resolv.conf!} dentro la nuova radice.
\end{enumerate}

Tuttavia, l'uso di NsJail per separare gli ambienti dei partecipanti,
rende difficoltosa l'implementazione di challenge in cui si vuole dare
la libertà ai partecipanti di installare pacchetti dentro al container,
oppure di modificare file di configurazione che risiedono per esempio in
\passthrough{\lstinline!/etc!} e di modificare direttamente servizi in
esecuzione sul container. \footnote{\label{fn:ref_6}Google Security Team, \emph{kCTF
  Security and Threat Model},
  https://github.com/google/kctf/blob/v1/docs/security-threat-model.md}

Queste limitazioni ci sono perché NsJail nell'ambiente sandbox non
fornisce una propria istanza di \passthrough{\lstinline!systemd!} (o un
qualsiasi gestore di servizi) e neanche l'infrastruttura necessaria per
eseguire comandi come \passthrough{\lstinline!apt!}.

NsJail porta con sé altri problemi:

\begin{itemize}
\tightlist
\item
  Se dovesse cadere la connessione TCP allora tutto il contenuto del
  filesystem in RAM andrebbe perso.
\item
  L'uso di \passthrough{\lstinline!seccomp!} per filtrare le chiamate di
  sistema potrebbe impedire l'esecuzione di alcuni programmi essenziali
  per la challenge.
\end{itemize}

Dunque kCTF potrebbe essere utilizzato per implementare un Cyber Range
difensivo ma con varie limitazioni e problemi da aggirare.

L'approccio di kCTF è completamente all'opposto di quanto fatto in
BlueAgent ed in altri Cyber Range. BlueAgent si occupa di gestire più
container per ogni team, mentre kCTF assegna un container per tutti i
team da dividere usando ambienti separati con NsJail.
