## 4.3 Struttura di una Challenge

In BlueAgent, la definizione di un esercizio o servizio di gara adotta il paradigma *Infrastructure-as-Code* (IaC): l'intera topologia di una challenge viene descritta mediante un file di specifica dichiarativo in formato YAML. 

Questo file specifica i container che compongono l'ambiente del team, le risorse hardware assegnate a ciascuno di essi e la logica di test necessaria per convalidarne il corretto funzionamento.

---

### 4.3.1 Struttura del File di Configurazione della Challenge

La struttura della specifica è articolata nelle seguenti sezioni principali:

1. **Metadati e Identificazione:**
   * `challenge_id`: Identificativo univoco della challenge.
   * `team_k`: Indice numerico del team proprietario dell'infrastruttura ($0 \le k \le 254$).
   * `verify_internet_access`: Flag booleano che determina se la sandbox effimera di verifica deve avere accesso a Internet (tramite NAT instradato su $\text{incusbr0}$) o rimanere confinata in una rete scura priva di uscite esterne.

2. **Topologia dei Container (`containers`):**
   Rappresenta la lista delle macchine che compongono la sfida (ad esempio un'applicazione web e il rispettivo database). Per ciascun container vengono dichiarati:
   * `name`: Nome logico dell'istanza all'interno della challenge.
   * `image`: Alias dell'immagine Incus da istanziare (ad esempio `ubuntu-heavy` o `alpine`).
   * `ip_suffix`: Ultimo ottetto dell'indirizzo IP statico assegnato al container (`10.k.1.X`), dove l'indirizzo `10.k.1.1` è riservato al gateway di produzione (`br-team-k`) o di verifica (router OVN).
   * `limits_cpu` e `limits_memory`: Vincoli hardware imposti tramite cgroup (ad esempio `1` vCPU e `256MB` di memoria RAM).

3. **Runner di Verifica Effimero (`verifier`, opzionale):**
   Definisce un container di test dedicato, istanziato esclusivamente durante la fase di verifica all'interno della rete scura OVN. Possiede una propria immagine (dotata di strumenti di probing o test, come Python o cURL), un IP dedicato (`10.k.1.250`) e vincoli di risorse isolati.

4. **Comandi di Readiness (`readiness_commands`):**
   Serie di controlli preliminari eseguiti all'avvio della sandbox per accertarsi che i servizi interni abbiano completato la fase di bootstrap (ad esempio attendere che un database risponda a un comando di ping o che un socket TCP sia in ascolto) prima di invocare i test veri e propri. Ciascun comando include intervalli di retry e policy di timeout.

5. **Comandi di Verifica (`verify_commands`):**
   Rappresentano la suite di convalida che certifica se il servizio è funzionante e se le condizioni di sicurezza sono soddisfatte. BlueAgent supporta due modalità operative distinte:
   * **In-Container (`target: "container"`):** Il comando viene eseguito direttamente dentro il container di produzione clonato tramite l'interfaccia di esecuzione di Incus (`incus exec`), permettendo di verificare file di sistema, permessi o integrità di processi locali (approccio *white-box*).
   * **Verifier Runner (`target: "verifier"`):** Il comando viene eseguito dall'interno del container `verifier` affacciato sulla rete logica OVN. Da questa postazione, il runner interroga i container del team tramite il loro indirizzo IP (`10.k.1.x`), simulando le richieste di un utente legittimo o le interazioni di un attaccante esterno (approccio *black-box*).

> `Verifica Black-Box vs White-Box`: La modalità *In-Container* opera dall'interno del filesystem per verificare che i processi e le configurazioni non siano stati alterati in modo distruttivo. La modalità *Verifier Runner* opera invece a livello di rete attraverso lo switch logico OVN, accertando che il servizio eroghi correttamente le sue funzionalità e risponda ai controlli di integrità del gioco.

### 4.3.2 Configurazione delle Immagini con Distrobuilder

Per garantire che le challenge siano riproducibili e sicure, BlueAgent non utilizza immagini generiche o preconfezionate, ma gestisce la compilazione di immagini container su misura tramite **Distrobuilder**.

> `Distrobuilder`: È lo strumento open source ufficiale del progetto Linux Containers utilizzato per creare immagini di sistema per Incus ed LXC a partire da alberi di pacchetti e distribuzioni upstream ufficiali (quali Ubuntu, Debian, Alpine o Arch Linux).

La configurazione di un'immagine in Distrobuilder avviene mediante un file dichiarativo concettualmente suddiviso in tre elementi fondamentali:

1. **Sorgente e Distribuzione (`image` e `source`):**
   Indica quale distribuzione Linux utilizzare come base, la release target (ad esempio Ubuntu 22.04 o Alpine 3.21) e l'architettura hardware di riferimento (`x86_64`). Distrobuilder scarica i pacchetti minimi certificati direttamente dai mirror ufficiali della distribuzione.

2. **Gestione dei Pacchetti (`packages`):**
   Definisce l'elenco dei software da installare all'interno del rootfs per preparare l'ambiente di gioco (ad esempio server web come Nginx o Apache, database server come PostgreSQL o SQLite, runtime interpretati come Python, e relativi moduli). È possibile inoltre rimuovere pacchetti superflui o demoni di telemetria per minimizzare l'impronta su disco.

3. **Fasi di Hook e Predisposizione Rete (`actions`):**
   Consente di eseguire script durante le fasi intermedie di generazione del filesystem (`post-unpack`, `post-packages`, `post-files`). In BlueAgent questo passaggio è essenziale per predisporre le directory dei demoni di rete (`/etc/systemd/network` per distribuzioni basate su `systemd` e `/etc/network` per distribuzioni con OpenRC/ifupdown). In questo modo il container è immediatamente compatibile con l'iniezione statica delle configurazioni IP eseguita da BlueAgent al momento del deploy.

All'interno dell'architettura di BlueAgent, il sottosistema `ImageService` invoca Distrobuilder generando un archivio compresso unificato (`--type=unified`). Il tarball generato viene importato nello storage pool ZFS, registrato con un alias univoco nel database locale e marcato come pronto, consentendo l'istanziazione immediata dei container durante le fasi di gara.
