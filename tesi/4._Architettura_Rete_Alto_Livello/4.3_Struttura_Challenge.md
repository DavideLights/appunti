## 4.3 Struttura e configurazione di una Challenge

In BlueAgent, la definizione di una challenge adotta l'approccio *Infrastructure-as-Code* (IaC): l'intera topologia viene descritta mediante uno o più file dichiarativi in formato YAML. 

Questo file specifica quali container compongono l'ambiente, le risorse hardware assegnate a ciascuno di essi ed i comandi di readiness e di verifica necessari per convalidarne la patch.

La configurazione della challenge avviene in due step:
* Specifica delle immagini Distrobuilder tramite file di configurazione.
* Configurazione della challenge vera e propria. Vengono specificati qui i container da istanziare e con quali immagini.

### 4.3.1 Struttura del File di Configurazione della Challenge

La struttura della specifica di una challenge è articolata nelle seguenti sezioni principali:
1. **Metadati e Identificazione:**
   * `challenge_id`: Identificatore alfanumerico univoco globale della sfida (ad esempio `patch-web-sqli`).
   * `team_k`: Indice numerico deterministico del team ($1 \le k \le 254$). 

2. **Topologia dei Container (`containers`):**
   Rappresenta la lista delle macchine che compongono la sfida. Per ciascun container vengono dichiarati:
   * `name`: Nome logico della macchina all'interno della challenge (ad esempio `web` o `database`).
   * `image`: Alias dell'immagine Incus da istanziare.
   * `ip_suffix`: Ultimo ottetto dell'indirizzo IP statico assegnato al container (`10.k.1.X`), dove `10.k.1.1` è riservato al gateway.
   * `limits_cpu` e `limits_memory`: Vincoli hardware imposti tramite cgroup.

3. **Runner di Verifica Effimero (`verifier`, opzionale):**
   Definisce un container di test dedicato, istanziato esclusivamente durante la fase di verifica all'interno della rete OVN (ad esempio con suffisso IP `250`).

4. **Comandi di Readiness (`readiness_commands`):**
   Serie di controlli preliminari eseguiti all'avvio della sandbox per accertarsi che i servizi interni abbiano completato la fase di bootstrap, prima di invocare i test veri e propri. Ciascun comando include intervalli di retry e policy di timeout.

5. **Comandi di Verifica (`verify_commands`):**
   Rappresentano la suite di convalida che certifica la patch. BlueAgent supporta due modalità operative distinte:
   * `target: container`: verifica in White Box eseguita direttamente all'interno dell'istanza bersaglio (ad esempio per verificare lo stato di un servizio con `systemctl`).
   * `target: verifier`: verifica in Black Box eseguita dal container tester per simulare l'attacco di rete o verificare l'integrità del servizio attraverso la LAN virtuale.

**Esempio di Configurazione YAML:**
Di seguito è riportato un esempio sintetico di descrittore dichiarativo per una challenge multi-tier composta da un'applicazione web e un database:

```yaml
challenge_id: "patch-web-sqli"
verify_internet_access: true

containers:
  - name: "database"
    image: "debian-12-mysql"
    ip_suffix: 3
    limits_cpu: "1"
    limits_memory: "512MB"

  - name: "web"
    ...

verifier:
  image: "verifier-python"
  ...

readiness_commands:
  - target: "container"
    container_name: "database"
    cmd: ["mysqladmin", "ping", "-h", "127.0.0.1"]
    retry: 2
    timeout: 15

verify_commands:
  - target: "container"
    container_name: "web"
    cmd: ["systemctl", "is-active", "--quiet", "flask-app"]
    timeout: 5
  - target: "verifier"
	...
```

**Parsing e Risoluzione Dinamica degli Indirizzi IP nei Comandi:**
Poiché la specifica YAML viene scritta dall'autore della sfida in modo indipendente dallo specifico team, i comandi non possono contenere indirizzi IPv4 cablati staticamente. BlueAgent implementa un meccanismo di template interno:

* `{{ip:<name>}}`: viene tradotto nell'indirizzo IPv4 completo `10.<team_k>.1.<ip_suffix>` associato al container con nome logico `<name>`.
* `{{subnet}}`: viene sostituito con il prefisso di rete assegnato al team (`10.<team_k>.1`).
* `{{verifier_ip}}`: corrisponde all'IP assegnato al runner di test (`10.<team_k>.1.<ip_suffix>`).
* `{{team_k}}`: viene sostituito dall'identificatore numerico del team.

### 4.3.2 Configurazione delle Immagini con Distrobuilder
> `Distrobuilder`: È lo strumento open source ufficiale per creare immagini di sistema per Incus ed LXC a partire da alberi di pacchetti e distribuzioni upstream ufficiali.

La configurazione di un'immagine in Distrobuilder avviene mediante un file dichiarativo. I campi principali sono i seguenti:

1. **Sorgente ed Immagine (`image` e `source`):**
   Indica quale immagine usare come base.

2. **Gestione dei Pacchetti (`packages`):**
   Definisce l'elenco dei software da installare all'interno del rootfs per preparare l'ambiente. È possibile anche rimuovere pacchetti preinstallati nell'immagine.

3. **Fasi di Hook e Predisposizione Rete (`actions`):**
   Consente di eseguire script durante le fasi intermedie di generazione del filesystem. È essenziale per predisporre le directory dei demoni di rete o specificare configurazioni interne al sistema.

All'interno dell'architettura di BlueAgent, il sottosistema `ImageService` invoca Distrobuilder per generare il tarball da importare nello storage pool ZFS.
