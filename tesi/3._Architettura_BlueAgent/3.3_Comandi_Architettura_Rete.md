# 3.3 Comandi per l'Architettura di Rete
Per andare a fondo nei dettagli implementativi e spiegare meglio alcuni concetti, sono riportati alcuni passaggi fondamentali nella configurazione dell'host che esegue BlueAgent.

# 3.3.1 configurare OVN
Qui riporto la configurazione per implementare la SDN. Il **piano dei dati** e' implementato da Open vSwitch (**OVS**) e deve esser configurato in modo che possa comunicare con Incus.

> `SDN (Software Defined Networking)`: Paradigma architetturale che separa il **Control Plane** (logica decisionale centralizzata) dal **Data Plane** (inoltro fisico dei pacchetti), consentendo di gestire e programmare l'infrastruttura di rete interamente via software.
>
> `Open vSwitch (OVS)`: Switch virtuale operante nel kernel Linux come Data Plane. Sostituisce il classico bridge Linux eseguendo l'inoltro dei frame ad alte prestazioni basandosi su tabelle di flussi (*flow tables*).
>
> `OpenFlow`: Protocollo standard che permette al controller SDN di comunicare con lo switch e programmare le regole di matching e le azioni direttamente all'interno delle pipeline di Open vSwitch.
>
> `OVN (Open Virtual Network)`: Sistema SDN che opera come Control Plane per Open vSwitch. Traduce topologie logiche (Logical Switch, Logical Router, NAT e ACL) in flussi OpenFlow distribuiti, istruendo Open vSwitch su come instradare il traffico senza creare molteplici interfacce o bridge dedicati nel kernel host.

**Configurazione di open vSwitch**:
```bash
sudo ovs-vsctl set open_vswitch . \ 
external_ids:ovn-remote=unix:/run/ovn/ovnsb_db.sock \ external_ids:ovn-encap-type=geneve \ 
external_ids:ovn-encap-ip=127.0.0.1
```
* **`ovn-encap-type=geneve`**: specifichiamo geneve come protocollo da utilizzare per il tunneling.
* **`ovn-encap-ip=127.0.0.1`**: imposta la terminazione del tunnel nel localhost.

> **Open vSwitch**: e' uno switch virtuale, software-definied. Agisce per la maggior parte in user space e comunica con il kernel per riceve i pacchetti ed inoltrarli.
> * `ovs-vswitchd`: e' il demone in user space. Ispeziona i pacchetti catturati dal kernel.
> * `ovsdb-server`: e' un database che memorizza la configurazione degli switch
> * `ovs-vsctl`: utility da riga di comando per la gestione dell'infrastruttura.
 

**Collegare l'interfaccia Northbound di OV ad Incus**:
```bash
ovn-nbctl set-connection ptcp:6641:127.0.0.1
incus config set network.ovn.northbound_connection tcp:127.0.0.1:6641
```

> * **OVN Northbound**: e' l'interfaccia dove dichiaro le reti che voglio creare e le loro proprietà che devono rispettare.
> * **`ovn-northd`**: il demone che traduce la topologia dichiarata tramite l'interfaccia north bound in stati logici.
> * **OVN Southbound (SB) DB:** Memorizza le tabelle di flussi logici compilate e le associazioni di chassis (host fisici) 
> - **`ovn-controller`:** Un agente in esecuzione sull'host che legge il Southbound DB e programma direttamente Open vSwitch locale.

## 3.3.2 $\text{production-}k$ Routing e Connettività dei Peer (WireGuard e nftables)

L'accesso dei partecipanti ai container rete $\text{production-}k$ richiede l'applicazione di regole di inoltro esplicite tra `wg-k` ed `br-team-k`, da applicare nel kernel Linux mediante `nftables`.

### Inoltro Kernel e Controllo di Flusso (`nftables`)
Le regole per il traffico vengono definite dentro la tabella `inet blueagent`:

```bash
sudo nft add table inet blueagent
sudo nft add set inet blueagent team_links '{ type ifname . ifname; flags interval; }'

sudo nft add element inet blueagent team_links { "wg-$k" . "br-team-$k", "br-team-$k" . "wg-$k" }
```

All'interno della catena `forward`, il traffico viene validato verificando l'appartenenza al set `@team_links` e scartando esplicitamente le comunicazioni incrociate tra team diversi. Vengono inserite esplicitamente per ogni `k` le coppie di interfacce per cui autorizzare il traffico.

A priori, si vuole impedire l'inoltro dei pacchetti applicando l'azione `drop` tra le interfacce `wg` e `br-team`, in modo da impedire rotte che non sono state esplicitamente accettate nella tabella:
```bash
sudo nft add rule inet blueagent forward iifname "wg-*" oifname "br-team-*" drop
sudo nft add rule inet blueagent forward iifname "br-team-*" oifname "wg-*" drop
sudo nft add rule inet blueagent forward iifname "br-team-*" oifname "br-team-*" drop
sudo nft add rule inet blueagent forward iifname "wg-*" oifname "wg-*" drop
```


### Connettività Egress (Masquerading)
Per consentire l'accesso a Internet ai container e ai peer, viene applicato il mascheramento dell'indirizzo sorgente verso l'esterno dell'envelope. Si abilita il `nat` (dunque, il meccanismo di traduzione degli indirizzi) poco prima che il frame esca e venga immesso fisicamente sulla porta. Poi specifichiamo che si applica il nat dinamico (`masquerade`) per gli indirizzi che provengono dalla rete dei container verso l'esterno.

```bash
sudo nft add chain inet blueagent postrouting '{ type nat hook postrouting priority srcnat; policy accept; }'
sudo nft add rule inet blueagent postrouting ip saddr 10.0.0.0/8 ip daddr != 10.0.0.0/8 masquerade
```
