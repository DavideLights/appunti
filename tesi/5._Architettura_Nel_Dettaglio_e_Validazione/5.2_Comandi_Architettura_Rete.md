# 5.2 Comandi per l'Architettura di Rete
Per andare a fondo nei dettagli implementativi e spiegare meglio alcuni concetti, sono riportati alcuni passaggi fondamentali nella configurazione della rete dell'host che esegue BlueAgent, o di comandi esguiti direttamente da BlueAgent.

# 5.2.1 configurare OVN
Qui riporto la configurazione per implementare la SDN. Il **piano dei dati** e' implementato da Open vSwitch (**OVS**) e deve esser configurato in modo che possa comunicare con Incus tramite l'interfaccia di OVN

Si configura OVS in modo che possa comunicare con l'interfaccia south bound di OVN (`ovnsb_db.sock`):
```bash
sudo ovs-vsctl set open_vswitch . \ 
external_ids:ovn-remote=unix:/run/ovn/ovnsb_db.sock \ external_ids:ovn-encap-type=geneve \ 
external_ids:ovn-encap-ip=127.0.0.1
```
* **`ovn-encap-type=geneve`**: Specifichiamo Geneve come protocollo da utilizzare per il tunneling. Questo passaggio e' necessario anche se non utilizziamo mai Geneve
* **`ovn-encap-ip=127.0.0.1`**: Imposta la terminazione del tunnel nel localhost.

Si configura invece l'interfaccia north bound in modo che possa comunicare con Incus:
```bash
ovn-nbctl set-connection ptcp:6641:127.0.0.1
incus config set network.ovn.northbound_connection tcp:127.0.0.1:6641
```

> **OVN Northbound**: e' l'interfaccia dove dichiaro le reti che voglio creare e le loro proprietà che devono rispettare.
> **OVN Southbound DB:** Memorizza le tabelle di inoltro e la logica da applicare sul piano dei dati.

## 5.2.2 $\text{production-}k$ Routing e Connettività dei Peer (WireGuard e nftables)

L'accesso dei partecipanti ai container rete $\text{production-}k$ richiede l'applicazione di regole di inoltro esplicite tra `wg-k` ed `br-team-k`, da applicare nel kernel Linux mediante `nftables`.

Le regole per il traffico vengono definite dentro la tabella `inet blueagent`:

```bash
sudo nft add table inet blueagent
sudo nft add set inet blueagent team_links '{ type ifname . ifname; flags interval; }'

sudo nft add element inet blueagent team_links { "wg-$k" . "br-team-$k", "br-team-$k" . "wg-$k" }
```

All'interno della catena `forward`, il traffico viene validato verificando l'appartenenza al set `@team_links` e scartando esplicitamente le comunicazioni incrociate tra team diversi. Vengono inserite esplicitamente per ogni `k` le coppie di interfacce per cui autorizzare il traffico.

A priori, si vuole impedire l'inoltro dei pacchetti applicando l'azione `drop` tra le interfacce `wg` e `br-team`, in modo da impedire rotte che non sono state esplicitamente accettate nella tabella:
```bash
sudo nft add rule inet blueagent forward iifname "wg-*" oifname "br-team-*" drop
sudo nft add rule inet blueagent forward iifname "br-team-*" oifname "wg-*" drop
sudo nft add rule inet blueagent forward iifname "br-team-*" oifname "br-team-*" drop
sudo nft add rule inet blueagent forward iifname "wg-*" oifname "wg-*" drop
```


Per consentire l'accesso a Internet ai container e ai peer, viene applicato il mascheramento dell'indirizzo sorgente verso l'esterno dell'envelope. Si abilita il `nat` (dunque, il meccanismo di traduzione degli indirizzi) poco prima che il frame esca e venga immesso fisicamente sulla porta. Poi specifichiamo che si applica il nat dinamico (`masquerade`) per gli indirizzi che provengono dalla rete dei container verso l'esterno.

```bash
sudo nft add chain inet blueagent postrouting '{ type nat hook postrouting priority srcnat; policy accept; }'
sudo nft add rule inet blueagent postrouting ip saddr 10.0.0.0/8 ip daddr != 10.0.0.0/8 masquerade
```
