# 1. Attori e Confini del Sistema

Nell'analisi formale dei casi d'uso della piattaforma BlueAgent, gli attori sono identificati e classificati in conformità ai principi dell'Ingegneria del Software (Cockburn / UML), distinguendo nettamente tra **Attori Primari di Sistema** (entità esterne che interagiscono direttamente con il confine del Control Plane), **Beneficiari / Stakeholder** (utenti finali dei servizi erogati) e **Componenti Interni di Sistema**.

---

### A. Attori Primari di Sistema (External System Actors)

1. **Piattaforma CTFd (Organizzatore di Gara / Upstream Master Orchestrator)**:
   - **Natura**: Sistema software esterno 
   - **Interazione**: Consuma le REST API esposte dal Control Plane FastAPI di BlueAgent, autenticandosi mediante token crittografico Bearer (`Authorization: Bearer <token>` o `X-CTFd-Token: <token>`).
   - **Responsabilità**: Governa programmaticamente l'intero ciclo di vita della competizione: richiede il provisioning e de-provisioning delle reti di team (`POST/DELETE /teams`), registra i concorrenti ed emette le configurazioni VPN WireGuard (`POST /teams/{team_k}/members`), raccoglie la telemetria peer in tempo reale (`GET /teams/{team_k}/peers`), orchestra il deploy delle sfide applicative (`POST /challenges`) e comanda le sessioni di verifica automatizzata (`POST /challenges/{id}/verify`).

2. **Autore della Sfida (Challenge Author / Red Teamer)**:
   - **Natura**: Utente umano specializzato (sviluppatore di scenari di sicurezza).
   - **Interazione**: Sottomette definizioni di immagini container tramite le API di build (`POST /images`) e progetta dichiarativamente la topologia multi-tier in formato YAML (`ChallengeConfig`).
   - **Responsabilità**: Fornisce le specifiche Distrobuilder (`definition.yaml`) per compilare le immagini di sistema unificate; definisce quote hardware cgroups v2, porte di rete, controlli di boot readiness e strategie dual-mode di verifica (white-box in-container e black-box via dark verifier runner).

3. **Amministratore di Sistema (SysAdmin / Monitoring)**:
   - **Natura**: Operatore umano o sonda automatica di infrastruttura (es. Prometheus / uptime monitor).
   - **Interazione**: Esegue le procedure di bootstrap e configurazione host iniziale (`host_setup.sh`) e interroga periodicamente l'endpoint pubblico di diagnostica e liveness probe (`GET /health`).
   - **Responsabilità**: Garantisce la corretta configurazione dei prerequisiti del kernel (moduli WireGuard, nftables, storage pool ZFS, bridge OVN/OVS) e controlla lo stato operativo dei socket e del demone.

---

### B. Beneficiari e Stakeholder (Secondary Actors / End Users)

* **Partecipante (Blue Teamer / Concorrente)**:
  - **Ruolo**: Utente finale e beneficiario primario del servizio di connettività e isolamento.
  - **Rapporto con il confine di sistema**: Il partecipante **non interagisce direttamente con il Control Plane BlueAgent**, bensì con la piattaforma CTFd (per ottenere le credenziali e richiedere le verifiche) e con la rete di gara (mediante il tunnel WireGuard `10.k.0.0/24`). Una volta stabilita la VPN, interagisce direttamente con i propri container sul bridge kernel `br-team-k` (`10.k.1.x`) per condurre ricognizione, analisi forense, hardening e patching del software vulnerabile.

---

### C. Componenti Architetturali Interni (Non-Actors)

* **`LifecycleManager` (Demone di Self-Healing e Riconciliazione)**:
  - **Natura**: Componente interno asincrono di BlueAgent, non un attore esterno.
  - **Funzione**: Esegue periodicamente (`reconcile_once`) la bonifica delle risorse di sandbox effimere orfane con prefisso `verify-`, applicando un grace period di 90 secondi. Realizza i requisiti non-funzionali di auto-guarigione, robustezza e prevenzione dei leak di risorse senza richiedere intervento umano.
