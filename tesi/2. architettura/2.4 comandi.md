### configurare OVN
Dobbiamo configurare il **piano dei dati**, implementato da Open vSwitch (**OVS**)

> **Open vSwitch**: e' uno switch virtuale, multistrato software-definied. Agisce per la maggior parte in user space e comunica con il kernel per riceve i pacchetti ed inoltrarli.
> * `ovs-vswitchd`: e' il demone in user space. Ispeziona i pacchetti catturati dal kernel.
> * `ovsdb-server`: e' un database che memorizza la configurazione degli switch
> * `ovs-vsctl`: utility da riga di comando per la gestione dell'infrastruttura.

> **OVN**: nelle reti di tipo **SDN**, OVN e' il software della rete che gestisce il **piano di controllo**, mentre Open vSwitch implementa il **piano dei dati**. 
> * **OVN Northbound**: e' l'interfaccia dove dichiaro le reti che voglio creare e le loro proprietà che devono rispettare.
> * **`ovn-northd`**: il demone che traduce la topologia dichiarata tramite l'interfaccia north bound in stati logici.
> * **OVN Southbound (SB) DB:** Memorizza le tabelle di flussi logici compilate e le associazioni di chassis (host fisici) 
> - **`ovn-controller`:** Un agente in esecuzione sull'host che legge il Southbound DB e programma direttamente Open vSwitch locale.

> **Tunneling**: e' lo stesso concetto su cui si basa wireguard. Vogliamo che una rete logica virtuale, possa attraversare su una rete sottostante, che funzioni d'appoggio per la comunicazione. In un tunnel, gli endpoint pensano di trovarsi sullo stesso switch fisico locale, ignorando come i pacchetti vengano inviati (attraverso una o piu reti). 
> Il tunneling, prende un intero pacchetto di rete e lo infila dentro un'altro pacchetto
> **Geneve**: e' un protocollo di incapsulamento dati per fare tunneling  tra interfacce.

**Configurazione di open vSwitch**:
```bash
sudo ovs-vsctl set open_vswitch . \ 
external_ids:ovn-remote=unix:/run/ovn/ovnsb_db.sock \ external_ids:ovn-encap-type=geneve \ 
external_ids:ovn-encap-ip=127.0.0.1
```
* **`ovn-encap-type=geneve`**: e' il protocollo per il tunneling utilizzato al livello L3
* **`ovn-encap-ip=127.0.0.1`**: imposta la terminazione del **tunnel** Geneve nel localhost.

**Metti l'interfaccia northbound in ascolto**:
```bash
sudo ovn-nbctl set-connection ptcp:6641:127.0.0.1
```

**Registra in incus indirizzo e porta per l'interfaccia northbound**:
```bash
sudo incus config set network.ovn.northbound_connection tcp:127.0.0.1:6641
```

**assegnazione indirizzi ad `incusbr0`**:
```bash
sudo incus network set incusbr0 ipv4.address=172.16.0.1/24 ipv4.nat=true

sudo incus network set incusbr0 ipv4.dhcp.ranges=172.16.0.2-172.16.0.99 ipv4.ovn.ranges=172.16.0.100-172.16.0.199

* `ipv4.ovn.ranges=172.16.0.100-172.16.0.199`: pool degli indirizzi ip per le interfacce ovn.

> Il router logico di OVN, pescherà un'indirizzo IP da `ipv4.ovn.ranges=172.16.0.100-172.16.0.199`

### setup della rete $\text{production-0}$: $\text{br-team-0}$ ed $\text{wg-0}$
**esempio di creazione della rete $\text{production-}0$:**
```bash
sudo ip link add name br-team-0 type bridge
sudo ip addr add 10.0.1.1/24 dev br-team-0
sudo ip link set dev br-team-0 up
```
* crea un nuovo device nel kernel linux, di tipo bridge
* assegnagli un'indirizzo ip, che funge da default gateway per i container collegati.
* porta in stato UP.

> `10.0.1.1`: 
> * `10.0`: perche' mi trovo nella rete $\text{production-}0$
> * `1.1`: e' il suffisso assegnato ai bridge per ogni rete $\text{production-}k$
  
**generazione chiavi crittografiche wireguard per server e client**:
```bash
wg genkey | tee wg-0-private.key | wg pubkey > wg-0-public.key

wg genkey | tee client-0-private.key | wg pubkey > client-0-public.key
```
* `wg-0-private.key`: contiene chiave pubblica e privata del server
* `client-0-private.key`: contiene chiave pubblica e privata  del client

**creazione device wireguard**: il device wireguard si crea similmente a quanto fatto per il bridge, e gli assegnamo l'IP `10.0.0.1/24`
```bash
sudo ip link add dev wg-0 type wireguard
sudo ip addr add 10.0.0.1/24 dev wg-0
```

> per ora nella rete, `10.0.0.1` e' il gateway, ossia l'interfaccia `wg-0`. Mentre posso utilizzare i restanti 254 indirizzi ip per assegnarli agli host che si connettono via **VPN**.

**demone wireguard**: mettiamo il demone wireguard in ascolto su $\text{wg-0}$
```bash
sudo wg set wg-0 listen-port 51820 private-key wg-0-private.key
sudo wg set wg-0 peer "$(cat client-0-public.key)" allowed-ips 10.0.0.2/32
sudo ip link set dev wg-0 up
```

### regole di routing per $\text{production-0}$

**rimuovere tutte le regole da una `table`** senza eliminarla:
```bash
sudo nft flush table inet blueagent 2>/dev/null || true
```

#### table `blueagent`
**creazione della table `blueagent`**:
```bash
sudo nft add table inet blueagent
```

> La tabella di inoltro server per permettere la comunicazione tra $\text{wg-0}$ ed $\text{br-team-0}$, al tempo stesso fornire la connettivita ad internet.
> Di default, il kernel linux non permette di comunicare tra due interfacce differenti sullo stesso host, dunque dobbiamo impostare una tabella di inoltro ad hoc per questo.
 
**chain forwarding nel kernel**: 
```bash
sudo nft add chain inet blueagent forward '{ type filter hook forward priority filter; policy accept; }'
```
* crea una nuova chain chiamata `forward` dentro `blueagent`
* `type filter`: specifica che la chain serve per il filtraggio dei pacchetti.
* `hook forward`: ancora la chain al kernel, nell'istante in cui si effettua l'inoltro dei pacchetti al livello L3.
	* In particolare la chain viene applicata quando il pacchetto arrivato sull'interfaccia non viene prelevato e consegnato all'host dal kernel.
* `priority filter`: esegui con priorità massima
* `policy accept`: accetta tutti i pacchetti che non fanno match su regole di blocco

> In pratica abbiamo **abilitato l'inoltro dei pacchetti** dentro la tabella di inoltro `blueagent`.

**applica la table su $\text{br-team-0}$:**
```bash
sudo nft add rule inet blueagent forward iifname "br-team-0" accept
sudo nft add rule inet blueagent forward oifname "br-team-0" accept
```
* `iifname`: **Input Interface Name**. Cattura qualsiasi pacchetto che entra nell'host provenendo da $\text{br-team-0}$
* * `oifname`: **Output Interface Name**. Cattura qualsiasi pacchetto che sta per uscire dall'host tramite $\text{br-team-0}$
* `accept`: applica il verdetto di accettazione, dunque abilito il traffico tra la rete dei container ed il kernel

**applica la table su $\text{wg-0}$**: similmente a quanto fatto prima
```bash
sudo nft add rule inet blueagent forward iifname "wg-0" accept
sudo nft add rule inet blueagent forward oifname "wg-0" accept
```
* `accept`: applica il verdetto di accettazione, dunque abilito il traffico tra l'inte rfaccia wireguard ed il kernel.

> In pratica diciamo al kernel di catturare il traffico da $\text{wg-0}$ e $\text{br-team-0}$ (se non viene bloccato prima, vedi $\text{accept}$) e di applicargli le regole di inoltro stanadrd.

**TCP, negoziazione MSS:**
```bash
sudo nft add rule inet blueagent forward tcp flags syn / syn,rst tcp option maxseg size set rt mtu
```

> Dato che applichiamo un tunnel con la connessione wireguard, il valore del MTU si abbassa di circa 80 byte. Per ridimensionare l'MSS di una connessione TCP possiamo manomettere il campo MSS dei pacchetti TCP tramite le regole di inoltro.

#### `NAT`

**Creazione della catena di NAT**:
```bash
sudo nft add chain inet blueagent postrouting '{ type nat hook postrouting priority srcnat; policy accept; }'
```
* `type nat`: abilita la traduzione degli indirizzi.
* `hook postrouting`: esegui la catena poco prima che il pacchetto esca dalla scheda di rete.
* `priority srcnat`: esegui la catena dopo che e' gia stato decisa la sorgente, da cui esce il pacchetto.

>  **`conntrack`**: creiamo l'infrastruttura necessaria per il nat e la tabella di tracciamento `conntrack`. Per ogni connessione che ha bisogno di instradare verso internet (che parta dal container o dalla connessione di un partecipante), il kernel deve tenere traccia di degli indirizzi ip coinvolti, la porta corrispondente sull'host per la sorgente e lo stato.


**Masquerade per la rete dei container**: applichiamo il mascheramento dell'indirizzo ip sorgente.
```
sudo nft add rule inet blueagent postrouting ip saddr 10.0.1.0/24 ip daddr != 10.0.1.0/24 masquerade
```
* **condizione 1**: se la sorgente e' un container (che si trovano nella sottorete `10.0.1.0/24`)
* **condizione 2**: se la destinazione non si trova nella sottorete dei container.
* **masquerade**: il kernel sovrascrive la sorgente dell'indirizzo con l'ip dell'host e si ricorda a quale porta corrisponde il container.

**Masquerade per la rete wireguard**:
```bash
sudo nft add rule inet blueagent postrouting ip saddr 10.0.0.0/30 ip daddr != 10.0.0.0/30 masquerade
```
* applico la stessa identica regola 

> Applicare **masquerade** (un tipo specifico di **NAT**) sulla rete dei container e sulla rete wireguard serve ad offrire la **connettività internet**.

### setup della rete $\text{verify-0}$:

**creazione interfaccia $\text{verify-ovn-0}$**:
```bash
VERIFY_UUID=0
sudo incus network create verify-ovn-${VERIFY_UUID} --type=ovn network=incusbr0 ipv4.address=10.0.1.1/24 ipv4.nat=true
```
* `ipv4.address=10.0.1.1/24`: chiedi ad `OVN` di avere un router con indirizzo uguale a quello di $\text{br-team-0}$
* `network=incusbr0`: per instradare verso internet usa il bridge standard di incus.
* `ipv4.nat=true`: applica NAT per mascherare i pacchetti dei container quando vanno verso internet.

**duplicazione container**:
```bash
sudo incus copy c0-web c0-web-v-${VERIFY_UUID} --instance-only
sudo incus config device override c0-web-v-${VERIFY_UUID} eth0 network=verify-ovn-${VERIFY_UUID} parent=
```

**avvio del container duplicato**:
```bash
sudo incus start c0-web-v-${VERIFY_UUID}
```

```nft
