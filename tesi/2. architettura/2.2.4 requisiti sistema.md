# Requisiti di Sistema e Requisiti Utente

Questo documento definisce in modo formale i **Requisiti Utente (UR)**, i **Requisiti di Sistema (SR)** e la **Matrice di Tracciabilità (UR ↔ SR)** della piattaforma BlueAgent, riflettendo fedelmente l'architettura reale, i moduli del codice sorgente e i vincoli operativi descritti nel contesto di riferimento.

---

## 1. Requisiti Utente (User Requirements)

Convenzione identificativa: **`UR-<CATEGORIA>-<ID>`**

### Categoria UR-ACC: Accesso, Connettività & User Experience
| Codice        | Titolo Requisito                            | Descrizione Operativa                                                                                                                                                                                | Ruolo Beneficiario |
| :------------ | :------------------------------------------ | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------- |
| **UR-ACC-01** | Connessione VPN dedicata e sicura           | Il partecipante deve poter accedere in modo esclusivo, cifrato e diretto al proprio ambiente di gara tramite un tunnel WireGuard dedicato, isolato dal traffico degli altri concorrenti.             | Partecipante       |
| **UR-ACC-02** | Topologia di rete uniforme e deterministica | Ogni squadra deve disporre della medesima topologia interna (`10.k.1.0/24`) e degli stessi indirizzi IP statici (es. Server Web su `.2`, Database su `.3`), senza disparità architetturali tra team. | Partecipante       |
| **UR-ACC-03** | Prestazioni I/O e latenza near-bare-metal   | Il concorrente deve interagire con i container a velocità nativa di bus RAM e bridge kernel L2, senza il degrado di throughput tipico delle reti virtuali SDN durante la fase di live game.          | Partecipante       |

### Categoria UR-CHL: Definizione Challenge & IaC
| Codice | Titolo Requisito | Descrizione Operativa | Ruolo Beneficiario |
| :--- | :--- | :--- | :--- |
| **UR-CHL-01** | Definizione dichiarativa via YAML (IaC) | L'autore della sfida deve poter descrivere l'intera architettura (servizi, immagini container, suffissi IP deterministici, quote hardware e comandi) tramite un manifesto YAML standard e versionabile. | Autore Sfida |
| **UR-CHL-02** | Ambienti multi-container e stateful | La piattaforma deve supportare scenari complessi multi-tier basati su container di sistema con sistema operativo completo (`systemd`, demoni multipli, persistenza dello stato su storage CoW). | Autore Sfida |
| **UR-CHL-03** | Quote e vincoli di risorse (Cgroups v2) | L'autore deve poter definire quote massime perentorie di CPU e memoria RAM per container per scongiurare attacchi DoS o starvation delle risorse del nodo host. | Autore Sfida |
| **UR-CHL-04** | Controlli di prontezza (Readiness Checks) | L'autore deve poter dichiarare sequenze di boot check (es. socket listening, ping database) eseguite prima di esporre la sfida ai concorrenti, con rollback atomico in caso di errore. | Autore Sfida |

### Categoria UR-VER: Verifica, Valutazione & Integrità
| Codice | Titolo Requisito | Descrizione Operativa | Ruolo Beneficiario |
| :--- | :--- | :--- | :--- |
| **UR-VER-01** | Verifica non distruttiva (Zero Live Crash) | L'esecuzione degli exploit di verifica o dei controlli di patch non deve alterare lo stato né mandare in crash l'ambiente di produzione vivo del team, proteggendone l'uptime SLA. | Partecipante / Organizzatore |
| **UR-VER-02** | Protezione da Side-Channel Leaks | I payload di exploit, gli script di validazione e le flag non devono essere intercettabili dai partecipanti (es. tramite packet sniffing `tcpdump` sul bridge live o ispezione log/processi). | Organizzatore / Autore |
| **UR-VER-03** | Dual-Mode Verification (Audit & Black-Box) | L'autore deve poter scegliere tra controlli white-box eseguiti dentro il clone (`target: "container"`) e attacchi black-box iniettati da un container runner effimero su rete L2 (`target: "verifier"`). | Autore Sfida |
| **UR-VER-04** | Risposta di verifica sub-secondaria | La piattaforma deve calcolare e ritornare l'esito della verifica in pochi secondi, sfruttando snapshot CoW istantanei a livello di blocco ($\sim 100\text{ ms}$). | Partecipante / Organizzatore |

### Categoria UR-ORG: Amministrazione, Orchestrazione & API
| Codice | Titolo Requisito | Descrizione Operativa | Ruolo Beneficiario |
| :--- | :--- | :--- | :--- |
| **UR-ORG-01** | Control Plane REST API programmabile | Tutte le funzionalità di ciclo di vita (creazione team, membri VPN, deploy sfide, verifica e teardown) devono essere richiamabili via API HTTP con token di autenticazione CTFd. | Organizzatore / CTFd |
| **UR-ORG-02** | Osservabilità e monitoraggio trasparente | Gli organizzatori devono poter monitorare e sniffare il traffico live dei team con i consueti strumenti di analisi Linux (`tcpdump -i br-team-k`) e telemetria peer (`GET /teams/{k}/peers`). | Organizzatore |
| **UR-ORG-03** | Bonifica e auto-guarigione (Self-Healing) | La piattaforma deve garantire la rimozione automatica delle sandbox e la terminazione delle risorse orfane in caso di crash imprevisti o timeout di verifica. | Organizzatore / Admin |

## 2. Requisiti di Sistema (System Requirements)

Convenzione identificativa: **`SR-<CATEGORIA>-<ID>`**

### Categoria SR-HST: Host & Piattaforma di Esecuzione
| Codice | Componente | Descrizione Tecnica | Riferimento Codice |
| :--- | :--- | :--- | :--- |
| **SR-HST-01** | OS & Moduli Kernel | Supporto target Debian 13 (Trixie) con kernel Linux moderno comprendente moduli WireGuard, cgroups v2 e supporto `nftables` con IP Forwarding abilitato (`net.ipv4.ip_forward=1`). | `scripts/host_setup.sh` |
| **SR-HST-02** | Storage Pool CoW | Configurazione di uno storage pool Incus su ZFS (denominato `blueagent-zfs`), capace di clonare container istantaneamente a livello di blocchi ($\le 100\text{ ms}$). | `src/blueagent/config.py`, `src/blueagent/engine/incus.py` |
| **SR-HST-03** | Demoni SDN Host | Presenza attiva di Open vSwitch e OVN (`ovs-vswitchd`, `ovsdb-server`, `ovn-northd`, `ovn-controller`) con listener TCP su `tcp:127.0.0.1:6641` per Incus. | `scripts/host_setup.sh` |
| **SR-HST-04** | Uplink Parent Bridge | Il bridge di sistema `incusbr0` deve dichiarare un intervallo di subnet allocabili OVN (`ipv4.ovn.ranges=172.16.0.100-172.16.0.199`) per connettere a monte le reti logiche effimere e consentire eventuale uscita WAN NAT. | `scripts/host_setup.sh` |

---

### Categoria SR-ENG: Motore di Containerizzazione & I/O
| Codice | Componente | Descrizione Tecnica | Riferimento Codice |
| :--- | :--- | :--- | :--- |
| **SR-ENG-01** | Interfaccia Astratta Engine | Implementazione dell'interfaccia astratta `ContainerEngine` per disaccoppiare la logica applicativa dal runtime sottostante (Incus/Docker). | `src/blueagent/engine/base.py` |
| **SR-ENG-02** | Client Asincrono UDS | `IncusEngine` deve comunicare via Unix Domain Socket (`/var/lib/incus/unix.socket`) mediante `httpx.AsyncClient` con corretta risoluzione dei percorsi relativi e gestione eccezioni HTTP. | `src/blueagent/engine/incus.py` |
| **SR-ENG-03** | Sincronizzazione Long-Polling | La sincronizzazione delle operazioni asincrone di Incus deve avvenire invocando l'endpoint `/1.0/operations/{uuid}/wait?timeout=N`, rilevando stati di `Success`, `Failure` o `Cancelled`. | `src/blueagent/engine/incus.py` |
| **SR-ENG-04** | Clonazione Snapshot CoW | Implementazione del metodo `clone_instance` basato su copia a livello di snapshot (`source={"type": "copy", "instance_only": True}`), con tempi medi di duplicazione $\le 100\text{ ms}$. | `src/blueagent/engine/incus.py` |
| **SR-ENG-05** | Isolamento Cgroups v2 | Applicazione delle quote hardware `limits.cpu` e `limits.memory` sulle istanze Incus per garantire confini prestazionali deterministici. | `src/blueagent/engine/incus.py` |

### Categoria SR-NET: Rete Ibrida, Routing & Traffico
| Codice | Componente | Descrizione Tecnica | Riferimento Codice |
| :--- | :--- | :--- | :--- |
| **SR-NET-01** | Tunnel WireGuard L3 Multi-Member | Per ciascun team $k$, creazione dell'interfaccia `wg-k` su subnet `10.k.0.1/24` (porta UDP `51820 + k`) con Cryptokey Routing associato alla chiave pubblica di ciascun membro (`AllowedIPs = 10.k.0.x/32`), allocazione dinamica con hole-filling nel range `.2`–`.254` (capacità 253 membri) e preshared key (PSK). | `src/blueagent/network/wireguard.py`, `src/blueagent/network/addressing.py` |
| **SR-NET-02** | Linux Bridge L2 Live | Per ciascun team $k$, allocazione di un bridge kernel `br-team-k` con IP gateway `10.k.1.1/24`, associato a un profilo Incus `team-k-profile` per l'aggancio diretto delle `veth`. L'IP statico deterministico (`10.k.1.x`) viene pre-configurato nel rootfs (`systemd-networkd` e `/etc/network/interfaces`) e forzato all'avvio con `ip addr replace`. | `src/blueagent/network/host_net.py` |
| **SR-NET-03** | Overlay OVN Dark Sandbox | Per ogni sessione di verifica, creazione di una rete SDN OVN effimera (`verify-{session_id[:4]}`, `ipv4.address: none`) su tunnel Geneve con isolamento totale dal traffico di produzione. | `src/blueagent/verifier/ovn.py` |
| **SR-NET-04** | Fedeltà Topologica & Zero Host Route Clash | Coesistenza simultanea della medesima subnet (`10.k.1.0/24`), stessi IP statici e singola interfaccia `eth0` sia in produzione che in verifica, senza generare rotte duplicate o conflitti nella tabella di routing del kernel Linux host. | `src/blueagent/verifier/ovn.py` |
| **SR-NET-05** | TCP MSS Clamping | Applicazione della regola nftables `tcp flags syn / syn,rst tcp option maxseg size set rt mtu` nella tabella `inet blueagent` per azzerare il fenomeno dell'MTU Blackhole tra WireGuard (MTU 1420) e Geneve (MTU 1442). | `src/blueagent/network/host_net.py` |
| **SR-NET-06** | NAT Masquerade | Configurazione del mascheramento postrouting nftables per la rete `10.0.0.0/8` verso l'uscita WAN fisica dell'host. | `src/blueagent/network/host_net.py` |

### Categoria SR-VRF: Motore di Verifica OVN (Dark Sandbox)
| Codice | Componente | Descrizione Tecnica | Riferimento Codice |
| :--- | :--- | :--- | :--- |
| **SR-VRF-01** | Async Context Manager | Incapsulamento dell'intero ciclo di verifica nella classe `OVNVerifier` con gestione asincrona atomica conforme al paradigma RAII (`__aenter__` / `__aexit__`). | `src/blueagent/verifier/ovn.py` |
| **SR-VRF-02** | Re-binding Dinamico `eth0` | Riconfigurazione a caldo dell'interfaccia `eth0` per i cloni target, dissociandola dal bridge `br-team-k` e associandola allo switch dark OVN `verify-{id[:4]}` senza assegnare `ipv4.address` sul device (evitando errori DHCP 500) e applicando l'IP nel namespace del container. | `src/blueagent/verifier/ovn.py` |
| **SR-VRF-03** | Verifier Container Effimero | Avvio opzionale di un container verifier runner (`verify-runner-xxxx`, `10.k.1.250`) collegato allo switch OVN per condurre test di penetrazione ed exploit simulando un attaccante esterno sulla medesima LAN. | `src/blueagent/verifier/ovn.py` |
| **SR-VRF-04** | Teardown Atomico Inverso (LIFO) | Chiusura e pulizia garantita delle risorse di verifica in ordine rigorosamente inverso: 1) arresto/rimozione verifier container $\rightarrow$ 2) arresto/rimozione cloni target $\rightarrow$ 3) distruzione switch logico OVN. | `src/blueagent/verifier/ovn.py` |
| **SR-VRF-05** | Esecuzione Comandi e Raccolta Log | Esecuzione sicura di comandi di verifica via `exec_command` con timeout vincolato e salvataggio puntuale di stdout, stderr e exit code. | `src/blueagent/engine/incus.py`, `src/blueagent/verifier/ovn.py` |

### Categoria SR-CON: Control Plane, Concorrenza & Ciclo di Vita
| Codice | Componente | Descrizione Tecnica | Riferimento Codice |
| :--- | :--- | :--- | :--- |
| **SR-CON-01** | REST API FastAPI | Esposizione di endpoint asincroni ad alta efficienza per la gestione di team (`/teams`), sfide (`/challenges`), verifiche (`/challenges/{id}/verify`), immagini (`/images`) e diagnostica (`/health`), protetti da autenticazione con Bearer token CTFd. | `src/blueagent/api/` |
| **SR-CON-02** | Two-Tier Lock Registry | Gestione della concorrenza tramite `TwoTierLock` (combinazione di `asyncio.Lock` per coroutine locali e `filelock.AsyncFileLock` su file system con reentrancy) per scongiurare errori `HTTP 409 Conflict` su mutazioni parallele dello stesso team. | `src/blueagent/locks.py` |
| **SR-CON-03** | Self-Healing & Grace Period | Background worker `LifecycleManager` per la bonifica automatica periodica delle sandbox orfane (`verify-*`) con grace period di 90 secondi per evitare race condition durante il provisioning legittimo. | `src/blueagent/lifecycle/manager.py` |
| **SR-CON-04** | Healthcheck & Status Probe | Endpoint pubblico `GET /health` per verificare la reattività del demone, l'accessibilità del socket Incus e lo stato operativo del background scheduler. | `src/blueagent/api/health.py` |

## 3. Matrice di Tracciabilità (UR ↔ SR)

La seguente matrice documenta la corrispondenza bidirezionale tra ciascun requisito utente (`UR`) e i requisiti tecnici di sistema (`SR`) che ne realizzano il soddisfacimento operativo:

| Requisito Utente (UR) | Requisiti di Sistema Corrispondenti (SR) | Meccanismo Architetturale di Risoluzione |
| :--- | :--- | :--- |
| **UR-ACC-01** (VPN Dedicata) | **SR-NET-01**, **SR-HST-01** | Generazione interfaccia `wg-k` e vincolo Cryptokey Routing `10.k.0.x/32` con Curve25519 e PSK. |
| **UR-ACC-02** (Topologia Uniforme) | **SR-NET-02**, **SR-NET-04**, **SR-MOD-01**, **SR-MOD-02** | Bridge kernel `br-team-k` e suffissi statici deterministici `10.k.1.x` pre-configurati nel rootfs. |
| **UR-ACC-03** (Prestazioni Native) | **SR-NET-02**, **SR-NET-05** | Traffico live su bridge kernel L2 esente da overhead OVS; clamping TCP MSS per evitare frammentazione. |
| **UR-CHL-01** (Configurazione IaC) | **SR-MOD-01**, **SR-MOD-02**, **SR-IMG-01** | Parsing dichiarativo YAML tramite modelli Pydantic v2 e catalogo immagini Distrobuilder. |
| **UR-CHL-02** (Multi-Container Stateful) | **SR-ENG-01**, **SR-ENG-02**, **SR-HST-02** | System container Incus con `systemd` e storage persistente CoW ZFS. |
| **UR-CHL-03** (Quote Risorse) | **SR-ENG-05**, **SR-MOD-01** | Applicazione quote cgroups v2 (`limits.cpu`, `limits.memory`) per ciascun container. |
| **UR-CHL-04** (Readiness Checks) | **SR-CON-01**, **SR-ENG-05** | Esecuzione sequenziale di controlli di boot durante il deploy (`POST /challenges`) con rollback atomico. |
| **UR-VER-01** (Zero Live Crash) | **SR-ENG-04**, **SR-VRF-01**, **SR-VRF-02** | Clonazione CoW istantanea ($\sim 100\text{ ms}$) ed esecuzione test esclusivamente sui cloni isolati. |
| **UR-VER-02** (No Side-Channel Leaks) | **SR-NET-03**, **SR-VRF-01** | Dark Sandbox su switch OVN Geneve isolata dal bridge live `br-team-k`, zero sniffing su produzione. |
| **UR-VER-03** (Dual-Mode Verification) | **SR-VRF-03**, **SR-VRF-05**, **SR-MOD-01** | Supporto congiunto per audit in-container (`target: "container"`) e container runner attaccante (`target: "verifier"`). |
| **UR-VER-04** (Verifica Rapida) | **SR-ENG-04**, **SR-ENG-03**, **SR-MOD-03** | Snapshot CoW a livello di blocco ZFS ($\le 100\text{ ms}$) e polling asincrono su socket Incus. |
| **UR-ORG-01** (Control Plane REST) | **SR-CON-01**, **SR-MOD-01**, **SR-CON-02** | Router FastAPI asincroni protetti da token CTFd e sincronizzati tramite `TwoTierLock`. |
| **UR-ORG-02** (Monitoraggio Live) | **SR-NET-02**, **SR-NET-01** | Sniffing non invasivo (`tcpdump -i br-team-k`) e telemetria peer live (`GET /teams/{k}/peers`). |
| **UR-ORG-03** (Bonifica Risorse) | **SR-VRF-04**, **SR-CON-03** | Teardown LIFO atomico via Context Manager RAII e background daemon `LifecycleManager` (grace period 90s). |
