# 2.1  CR Alternativi: kCTF

kCTF[^1] è una piattaforma sviluppata da Google, basata su *Kubernetes* e *nsjail*.

> *Kubernetes*: è un sistema open source per automatizzare il deploy, scalare e gestire applicazioni containerizzate.[^3]

> *NSJail*: ossia, NameSpace Jail, è un tool Linux per isolare i processi utilizzando varie feature del Kernel Linux come: namespaces, resource limits, seccomp-bpf syscall filters. L'obiettivo di NSJail è quello di creare un ambiente sicuro e isolato per eseguire le applicazioni. [^2]


![[src/images/kctf-architecture.png]]

Facendo riferimento alla Figura \ref{fig:kctf-architecture}, l'architettura di kCTF prevede:
* Un **cluster**, che contiene un insieme di challenge
* Dei **deployment**, ognuno contiene due container (o meglio, un Pod che istanzia 2 container):
	* un container `healthcheck`: usato per determinare lo stato di salute dei servizi
	* un container `challenge`: contiene i servizi su cui lavora lo sfidante.


> **Pod**: in Kubernetes, è la più piccola unità che Kubernetes può eseguire. Un Pod, rappresenta uno o più container in esecuzione su un singolo nodo.[^5]

> **Deployment**: in Kubernetes, un deployment è un template che specifica come creare i container. I template guidano la creazione di **Pods** e la gestione sicura del ciclo di vita di un Pod, in particolare la gestione dei ReplicaSet.[^5]


NSJail viene avviato su ogni container `challenge`, ed è configurato per ascoltare su una porta TCP nota. Ad ogni connessione TCP in arrivo, NSJail esegue un fork restituendo allo sfidante un ambiente separato (rispetto agli altri sfidanti) su cui lavorare. L'obiettivo di questa architettura è di poter riutilizzare lo stesso container per più sfidanti.

L'isolamento fornito da NSJail, si ottiene combinando varie tecniche:
* Creazione di nuovi namespace: l'ambiente fornito, esegue su un nuovo namespace, separando logicamente le risorse accessibili.
* Filtraggio delle chiamate di sistema tramite `seccomp-bpf`: questo sottosistema permette di uccidere i processi nell'ambiente se vengono eseguite chiamate di sistema vietate.
* Accounting e limitazione delle risorse con `cgroup`: questo sottosistema permette di monitorare e limitare le risorse utilizzabili nel nuovo ambiente.

NsJail può essere configurato in modo che ogni ambiente isolato, abbia a disposizione un filesystem temporaneo che risiede in RAM, mentre il filesystem originale è accessibile dall'ambiente sandbox in sola lettura. Questa configurazione è necessaria poiché altrimenti gli sfidanti modificherebbero tutti lo stesso filesystem.

Un'altra configurazione di NSJail è la seguente, ideale per le challenge di tipo `pwn` (trovare e sfruttare vulnerabilità in file binari):
```cfg
[...]
mount: [
  {
    src: "/chroot"
    dst: "/"
    is_bind: true
  },
  {
    dst: "/tmp"
    fstype: "tmpfs"
    rw: true
  },
  {
    dst: "/proc"
    fstype: "proc"
    rw: true
  },
  {
    src: "/etc/resolv.conf"
    dst: "/etc/resolv.conf"
    is_bind: true
  }
]
```
1. La cartella `/chroot` che risiede nel container, diventa la radice nel nuovo ambiente.
2. Viene creato un nuovo `tmpfs`, in `/tmp`
3. Viene importata la configurazione DNS da `/etc/resolv.conf` dentro la nuova radice.

Tuttavia, l'uso di NsJail per separare gli ambienti dei partecipanti, rende difficoltosa l'implementazione di challenge in cui si vuole dare la libertà ai partecipanti di installare pacchetti dentro al container, oppure di modificare file di configurazione che risiedono per esempio in `/etc` e di modificare direttamente servizi in esecuzione sul container. [^4]

Queste limitazioni ci sono perché NsJail nell'ambiente sandbox non fornisce una propria istanza di `systemd` (o un qualsiasi gestore di servizi) e neanche l'infrastruttura necessaria per eseguire comandi come `apt`.

NsJail porta con sé altri problemi:
* Se dovesse cadere la connessione TCP allora tutto il contenuto del filesystem in RAM andrebbe perso.
* L'uso di `seccomp` per filtrare le chiamate di sistema potrebbe impedire l'esecuzione di alcuni programmi fondamentali per la challenge.

Dunque kCTF potrebbe essere utilizzato per implementare un Cyber Range difensivo ma con varie limitazioni e problemi da raggirare.

L'approccio di kCTF è completamente all'opposto di quanto fatto in BlueAgent ed in altri Cyber Range. BlueAgent si occupa di gestire più container per ogni team, mentre kCTF assegna un container per tutti i team da dividere usando ambienti separati con NsJail.

Di seguito sono riportate le principali differenze tra kCTF e BlueAgent:
| Caratteristica | kCTF | BlueAgent |
| :--- | :--- | :--- |
| **Virtualizzazione** | Container applicativi e sandbox di processo (NSJail) | Container di sistema, ognuno con un suo gestore di servizi. |
| **Infrastruttura** | Cluster distribuito Kubernetes | Singolo nodo host  |
| **Ambiente Dedicato** | Un solo container condiviso tra sfidanti  | Container di sistema dedicati e separati per ciascun team |
| **Persistenza** | Filesystem effimero in RAM (`tmpfs`) | Persistente su disco |
| **Provisioning** | Istantaneo (consiste nel fork con NsJail) | Rapido (consiste nel deploy di uno o più container) |
