# 3.3 Requisiti di Sistema

I requisiti di sistema definiscono i vincoli architetturali, infrastrutturali e operativi che BlueAgent deve garantire per supportare i casi d'uso descritti. Di seguito vengono presentati, suddivisi nelle rispettive categorie funzionali, i requisiti formali di progetto.

## 3.3.1 Piattaforma Host e Infrastruttura

La tabella seguente riassume i requisiti relativi al sistema operativo host e ai componenti infrastrutturali di base necessari all'esecuzione di BlueAgent.

| Codice | Requisito | Descrizione Operativa |
| :-------------- | :--------------------- | :------------------------------------------------------------ |
| **`SR-HST-01`** | Sistema Operativo Host | L'host deve eseguire un kernel Linux, con IP forwarding abilitato e supporto completo per il sottosistema `nftables`.                                        |
| **`SR-HST-02`** | Storage Pool ZFS       | L'host deve disporre di uno storage pool ZFS (`blueagent-zfs`) con supporto nativo a snapshot Copy-on-Write (CoW).                                           |
| **`SR-HST-03`** | Servizi SDN Host       | L'host deve eseguire i demoni Open vSwitch e OVN (`ovs-vswitchd`, `ovn-northd`, `ovn-controller`) per il provisioning dinamico degli switch logici effimeri. |
| **`SR-HST-04`** | Supporto WireGuard     | L'host deve fornire il modulo kernel WireGuard e i relativi strumenti di configurazione.                                                                     |
| **`SR-HST-05`** | Pipeline Distrobuilder | L'host deve disporre di `distrobuilder` per la compilazione automatizzata e riproducibile delle immagini dei container.                                      |

## 3.3.2 Motore di Containerizzazione

I requisiti per il motore di containerizzazione stabiliscono i meccanismi di interazione con Incus, l'isolamento dei carichi e la gestione del ciclo di vita dei container di sistema.

| Codice | Requisito | Descrizione Operativa |
| :-------------- | :--------------------- | :------------------------------------------------------------ |
| **`SR-ENG-01`** | Astrazione del Motore            | Disaccoppiamento della logica di orchestrazione tramite l'interfaccia astratta `ContainerEngine`.                           |
| **`SR-ENG-02`** | Client Asincrono UDS             | Comunicazione non bloccante con Incus via Unix Domain Socket (`/var/lib/incus/unix.socket`) mediante client HTTP asincrono. |
| **`SR-ENG-03`** | Limitazione Risorse (Cgroups v2) | Applicazione di quote hardware per impedire la starvation delle risorse dell'host.                                            |
| **`SR-ENG-04`** | Clonazione Snapshot CoW          | Duplicazione istantanea delle istanze container basata su snapshot CoW a livello di storage pool ZFS.                       |

## 3.3.3 Rete Ibrida e Connettività

Questa sezione elenca i requisiti di rete necessari a garantire prestazioni native in fase di gara e isolamento crittografico per ogni squadra.

| Codice | Requisito | Descrizione Operativa |
| :-------------- | :--------------------- | :------------------------------------------------------------ |
| **`SR-NET-01`** | Gateway VPN WireGuard            | Allocazione di un'interfaccia kernel `wg-k` per ciascun team $k$, in ascolto sulla porta UDP $51820 + k$ con indirizzo gateway `10.k.0.1/24`.                                       |
| **`SR-NET-02`** | Linux Bridge L2 Live             | Allocazione di un bridge Linux `br-team-k` per ciascun team $k$, con gateway `10.k.1.1/24`.                                                                                         |
| **`SR-NET-03`** | Indirizzamento e Credenziali VPN | Allocazione deterministica degli IP dei membri nella subnet `10.k.0.0/24`.                                                                                                          |
| **`SR-NET-04`** | Topologia Deterministica         | Configurazione statica degli indirizzi IP `10.k.1.x` nei container in base al suffisso (`ip_suffix`) dichiarato nella specifica della challenge.                                    |
| **`SR-NET-05`** | TCP MSS Clamping                 | Applicazione di regole `nftables` per forzare il clamping del MSS, prevenendo pacchetti persi dovuti al tunnel WireGuard.                                                           |
| **`SR-NET-06`** | Isolamento e Masquerading NAT    | Isolamento inter-team tramite il set `@team_links` e masquerading del traffico outbound verso la rete esterna per l'accesso a Internet per giocatori, container e rete di verifica. |

## 3.3.4 Motore di Verifica OVN Sandbox

I requisiti del motore di verifica definiscono le garanzie di non interferenza, trasparenza e sicurezza durante l'esecuzione degli exploit e dei test di integrità.

| Codice | Requisito | Descrizione Operativa |
| :-------------- | :--------------------- | :------------------------------------------------------------ |
| **`SR-VRF-01`** | Switch Logico OVN              | Provisioning di uno switch virtuale OVN (`verify-<session>`) senza esporre il gateway all'host per evitare collisioni di rotte tra container. |
| **`SR-VRF-02`** | Fedeltà Topologica             | I cloni nella sandbox preservano l'interfaccia `eth0` e la medesima configurazione IP (`10.k.1.x`) specificata.              |
| **`SR-VRF-03`** | Readiness Probes e Timeout     | Esecuzione preliminare dei controlli di prontezza sui servizi con tentativi periodici, prima dell'esecuzione dei check di verifica.           |
| **`SR-VRF-04`** | Confinamento Zero Side-Channel | Isolamento del traffico di verifica sullo switch OVN per impedire qualsiasi sniffing (es. `tcpdump`) da parte dei concorrenti.               |
| **`SR-VRF-05`** | Rilascio Automatico Risorse    | Deallocazione automatica e atomica di cloni, switch e porte virtuali al termine della verifica o su eccezione.                                |

## 3.3.5 Control Plane, Concorrenza e Persistenza

La tabella seguente specifica i vincoli di sincronizzazione, resilienza e coerenza dello stato applicativo gestiti dal control plane di BlueAgent.

| Codice | Requisito | Descrizione Operativa |
| :-------------- | :--------------------- | :------------------------------------------------------------ |
| **`SR-CON-01`** | Two-Tier Lock Registry         | Meccanismo di lock gerarchico a due livelli per prevenire race condition sulle risorse.                                |
| **`SR-CON-02`** | Self-Healing e Riconciliazione | Demone `LifecycleManager` per la bonifica automatica degli switch e cloni orfani.                                      |
| **`SR-CON-03`** | Healthcheck & Telemetria Live  | Endpoint `/health` per ottenere lo stato di salute del sistema. Raccolta telemetrica dello stato dei peer WireGuard.   |
| **`SR-CON-04`** | Persistenza Asincrona SQLite   | Memorizzazione dello stato di team, membri, container e cataloghi su database SQLite.                                  |
| **`SR-CON-05`** | Rollback Atomico su Errore     | Qualsiasi fallimento durante il provisioning di container o interfacce di rete innesca la deallocazione delle risorse. |
| **`SR-CON-06`** | Idempotenza Operativa          | Tutte le richieste di creazione e configurazione per risorse già esistenti non generano errori applicativi.            |
| **`SR-CON-07`** | Autenticazione Centralizzata   | Validazione obbligatoria dell'accesso a tutti gli endpoint  tramite token segreto condiviso.                           |

## 3.3.6 Pipeline Immagini Distrobuilder

I requisiti della pipeline stabiliscono la creazione riproducibile delle immagini per le sfide, il loro tracciamento e il caching dei binari.

| Codice | Requisito | Descrizione Operativa |
| :-------------- | :--------------------- | :------------------------------------------------------------ |
| **`SR-IMG-01`** | Definizione IaC Distrobuilder     | Creazione dichiarativa di immagini per container di sistema a partire da manifesti YAML versionabili.                                   |
| **`SR-IMG-02`** | Caching e Identificazione SHA-256 | Tracciamento crittografico della specifica YAML tramite hash SHA-256 per identificare modifiche su immagini già compilate nel database. |
| **`SR-IMG-03`** | Compilazione Asincrona            | Esecuzione delle fasi di build e import Incus in background tramite task asincrono con tracciamento dei log.                            |
