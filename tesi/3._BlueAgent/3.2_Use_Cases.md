# 2.3 Use Cases per CTF Manager
Sono elencati di seguito gli Use Case per il CTF Manager, arricchito con alcuni dettagli implementativi per comprendere al meglio l'architettura del software. 

Di seguito e' riportato un  breve glossario:
> `br-team-k`: e' il bridge di rete che fornisce una rete locale per i container del team $k$. Ogni `br-team-k` e' logicamente separato dagli altri `br-team-k`.

> `wg-k`: e' l'interfaccia WireGuard che offre la connettivita VPN per il team $k$ verso `br-team-k`.

> `eth0`: in questo documento, spesso identifica il nome dell'interfaccia che fornisce la connettivita alla LAN per un container.

> `verify-k`: e' il bridge di rete (gestito tramite SDN) utilizzato per implementare la rete di verifica per il team `k`. Questa rete e' completamente scollegata da `br-team-k` e da `wg-k`.

> `database`: e' il database SQL, usato da BlueAgent per tenere traccia delle risorse allocate.


## `UC-01`: Deploy dell'infrastruttura di rete per il team $k$
* **Attore**: CTF Manager
* **Obiettivo**: Effettuare il deploy delle interfacce di rete necessarie al team $k$ per eseguire i container e consentire l'accesso VPN ai partecipanti.
* **Precondizione**: BlueAgent e' attivo ed e' raggiungibile via API REST.

Flusso delle azioni:
1. Il CTF Manager invia la richiesta `POST /teams`, specificando l'identificativo $k$ del team ed il relativo nome.
2. BlueAgent verifica se l'infrastruttura per il team $k$ esiste gia:
    1. Se il team e' gia registrato, risponde `HTTP 200 OK`.
    2. Altrimenti, l'infrastruttura di rete viene creata da zero:
        1. Viene creato il bridge `br-team-k` per il team $k$ con IP per il gateway `10.k.1.1/24`.
        2. Viene creata l'interfaccia WireGuard `wg-k` per il team $k$. La porta UDP e' `51820+k`, l'IP per il gateway e' `10.k.0.1/24`.
        3. Viene registrato il team all'interno del database.
        4. BlueAgent risponde con stato `HTTP 201 Created` confermando l'avvenuta creazione.

Se avviene un errore irrimediabile durante la creazione, il bridge e l'interfaccia WireGuard create vengono rilasciate.

## `UC-02`: Deploy della challenge per il team $k$
* **Attore**: CTF Manager
* **Obiettivo**: Effettuare il deploy dei container necessari alla challenge da allestire per il team $k$ richiedente.
* **Precondizione**: `UC-01`, `UC-08`. E' stato eseguito con successo il deploy dell'infrastruttura di rete per il team $k$ e le immagini dei container richieste sono presenti nel sistema.

Flusso delle azioni:
1. Il CTF Manager invia la richiesta `POST /teams/{team_k}/machines` specificando `team_k`.
2. BlueAgent valida le precondizioni.
3. Per ogni container specificato nella configurazione:
    1. Crea l'istanza del container.
    2. Collega l'interfaccia virtuale `eth0` dell'istanza al bridge del team `br-team-k`.
    3. Inietta nel filesystem dell'istanza la configurazione di rete statica.
    4. Avvia l'istanza del container ed applica l'indirizzo IP statico.
    5. Registra il container nel database.
4. BlueAgent restituisce la risposta con stato `HTTP 201 Created`.

Se si verifica un errore durante l'avvio, BlueAgent arresta ed elimina tutte le istanze e le risorse create fino a quel momento per la challenge e risponde con un errore.

## `UC-03`: Verifica della challenge per il team $k$
* **Attore**: CTF Manager
* **Obiettivo**: Verificare l'integrita dei servizi e l'efficacia delle patch applicate dal team mediante l'esecuzione dei comandi specificati nella configurazione della challenge.
* **Precondizioni**: `UC-02`. I container relativi alla challenge specificata per il team $k$ sono attivi.

Flusso delle azioni:
1. Il CTF Manager invia la richiesta `POST /teams/{team_k}/verificator` trasmettendo la configurazione della challenge da verificare.
2. Se una verifica per lo stesso team e' gia in corso, BlueAgent risponde con `HTTP 409 Conflict`.
3. Altrimenti, BlueAgent predispone l'ambiente di verifica:
    1. Crea uno switch virtuale denominato `verify-k`.
    2. Esegue la clonazione di tutti i container della challenge del team $k$.
    3. Riconfigura l'interfaccia `eth0` dei cloni agganciandola allo switch di verifica.
    4. Avvia i cloni sandbox e configura al loro interno lo stesso indirizzo IP statico di produzione `10.k.1.{ip_suffix}/24`.
    5. Se specificato nella configurazione, avvia un container di verifica.
4. Esecuzione dei controlli di verifica: viene eseguito un ciclo di tentativi finche' il comando non ha successo, oppure fino allo scadere del timeout.
5. Esegue i comandi di verifica all'interno del container specificato.
6. Dealloca le risorse sandbox create per il controllo.
7. BlueAgent risponde con stato `HTTP 200 OK` comunicando l'esito della verifica.

Se si verifica un errore le risorse utilizzate vengono rilasciate e viene comunicato l'errore.

## `UC-06`: Dismissione e rilascio di una challenge per il team $k$
* **Attore**: CTF Manager
* **Obiettivo**: Rimuovere tutti i container associati a una determinata challenge per il team $k$.
* **Precondizioni**: I container associati alla challenge specificata sono attivi per il team $k$.

Flusso delle azioni:
1. Il CTF Manager invia la richiesta `DELETE /teams/{team_k}/machines` specificando nel payload la configurazione della challenge.
2. Per ciascun container specificato nella configurazione della challenge:
    1. Arresta l'istanza.
    2. Elimina l'istanza.
    3. Cancella il record del container dal database.
3. BlueAgent risponde con stato `HTTP 204 No Content`.

In caso di problemi durante il teardown di uno o piu container, BlueAgent restituisce un errore HTTP con i dettagli dell'anomalia.

## `UC-08`: Compilazione e Import di un'immagine per container
* **Attore**: CTF Manager
* **Obiettivo**: Inviare la specifica di un'immagine in formato YAML ed avviare la compilazione e l'importazione nel catalogo delle immagini.
* **Precondizione**: BlueAgent e' attivo.

Flusso delle azioni:
1. Il CTF Manager invia una richiesta `POST /images` inviando una form multipart con il file di definizione YAML.
2. BlueAgent valida la specifica YAML e ne calcola l'hash crittografico.
3. BlueAgent verifica lo stato dell'immagine nel database:
    1. Se l'immagine con lo stesso alias o hash esiste gia, risponde immediatamente con `HTTP 200 OK`.
    2. Altrimenti, registra un nuovo record nel database.
4. BlueAgent avvia la compilazione tramite un worker asincrono:
    1. Importa l'immagine generata nel catalogo dei container.
    2. Assegna l'alias all'immagine importata e aggiorna il record nel database.
5. BlueAgent restituisce immediatamente al CTF Manager lo stato `HTTP 202 Accepted`.

## `UC-12`: Registrazione e configurazione WireGuard per un membro del team $k$
* **Attore**: CTF Manager
* **Obiettivo**: Registrare un giocatore come membro del team $k$, allocare un indirizzo IP nella subnet VPN, generare le chiavi crittografiche WireGuard e restituire il file di configurazione `.conf`.
* **Precondizioni**: BlueAgent e' attivo. Se l'infrastruttura di rete del team $k$ non e' ancora attiva, viene allestita contestualmente.

Flusso delle azioni:
1. Il CTF Manager invia la richiesta `POST /teams/{team_k}/members` fornendo nome ed id dell'utente.
2. BlueAgent verifica se l'infrastruttura del team $k$ e' attiva; se assente, esegue `UC-01`.
3. BlueAgent verifica se il membro e' gia registrato nel database per il team $k$:
    1. Se il membro esiste gia, BlueAgent fornisce la configurazione rispondendo con `HTTP 200 OK`.
    2. Se il membro e' nuovo:
        1. Alloca un indirizzo IP VPN libero per il team. Se lo spazio degli indirizzi e' esaurito, risponde segnalando l'esaurimento degli indirizzi.
        2. Se non fornita, genera una nuova coppia di chiavi asimmetriche.
        3. Registra il nuovo peer sull'interfaccia `wg-k`.
        4. Salva il record del membro nel database.
4. BlueAgent risponde con stato `HTTP 201 Created` restituendo la configurazione WireGuard generata.
