# 1.3.1 CR Alternativi: kCTF

kCTF[^1] e' una piattaforma sviluppata da Google, basata su *Kubernetes* e *nsjail*.

> *Kubernetes*: e' un sistema open source per automatizzare il deploy, scalare e gestire applicazioni containerizzate.[^3]

> *NSJail*: ossia, NameSpace Jail, e' un tool Linux per isolare i processi utilizzando varie feature del Kernel Linux come: namespaces, resource limits, seccomp-bpf syscall filters. L'obiettivo di NSJail e' quello di creare un'ambiente sicuro e isolato per eseguire le applicazioni. [^2]


![[src/images/kctf-architecture.png]]

Facendo riferimento all'immagine sopra, l'architettura di kCTF prevede:
* Un **cluster**, che contiene un'insieme di challenge
* Dei **deployment**, ognuno contiene due container (o meglio, un Pod che instanzia 2 container):
	* un container `healthcheck`: usato per determinare lo stato di salute dei servizi
	* un container `challenge`: contiene i servizi su cui lavora lo sfidante.


> **Pod**: in Kubernetes, e' la piu piccola unita che Kubernetes puo' eseguire. Un Pod, rappresenta uno o piu container in esecuzione su un singolo nodo.[^5]

> **Deployment**: in Kubernetes, un deployment e' un template che specifica come creare i container. I template guidano la creazione di **Pods** e la gestione sicura del ciclo di vita di un Pod, in particolare la gestione dei ReplicaSet.[^5]


NSJail viene avviato su ogni container `challenge`, ed e' configurato per ascoltare su una porta TCP nota. Ad ogni connessione TCP in arrivo, NSJail esegue un fork restituendo allo sfidante un'ambiente separato (rispetto agli altri sfidanti) su cui lavorare. L'obiettivo di questa architettura e' di poter riutilizzare lo stesso container per piu sfidanti.

L'isolamento fornito da NSJail, si ottiene combinando varie tecniche:
* Creazione di nuovi namespace: l'ambiente fornito, esegue su un nuovo namespace, separando logicamente le risorse accessibili.
* Filtraggio delle chiamate di sistema tramite `seccomp-bpf`: questo sottosistema permette di uccidere i processi nell'ambiente se vengono eseguite chiamate di sistema vietate.
* Accounting e limitazione delle risorse con `cgroup`: questo sottosistema permette di monitorare e limitare le risorse utilizzabili nel nuovo ambiente.

NsJail puo' essere configurato in modo che ogni ambiente isolato, abbia a disposizione un'filesystem temporaneo che risiede in RAM, mentre il filesystem originale e' accessibile dall'ambiente sandbox in sola lettura. Questa configurazione e' necessaria poiche altrimenti gli sfidanti modificherebbero tutti lo stesso filesystem.

Un'altra configurazione di NSJail e' la seguente: che e' ideale per le challenge di tipo `pwn` (trovare e sfruttare vulnerabilita in file binari):
```cfg
[...]
mount: [
  {
    src: "/chroot"
    dst: "/"
    is_bind: true
  },
  {
    dst: "/tmp"
    fstype: "tmpfs"
    rw: true
  },
  {
    dst: "/proc"
    fstype: "proc"
    rw: true
  },
  {
    src: "/etc/resolv.conf"
    dst: "/etc/resolv.conf"
    is_bind: true
  }
]
```
1. La cartella `/chroot` che risiede nel container, diventa la radice nel nuovo ambiente.
2. Viene creato un nuovo `tmpfs`, in `/tmp`
3. Viene importata la configurazione DNS da `/etc/resolv.conf` dentro la nuova radice.

Tutta via, l'uso di NsJail per separare gli ambienti dei partecipanti, rende difficoltosa l'implementazione di challenge in cui si vuole dare la liberta ai partecipanti di installare pacchetti dentro al container, oppure di modificare file di configurazione che risiedono per esempio in `/etc` e di modificare direttamente servizi in esecuzione sul container. [^4]

Queste limitazioni ci sono perche NsJail nell'ambiente sandbox non fornisce una propria istanza di `systemd` (o un qualsiasi gestore di servizi) e neanche l'infrastruttura necessaria per eseguiure comandi come `apt`.

Tale limitazione, porta ad escludere kCTF come possibile soluzione al problema orignale esposto, suggerendo come astrazione migliore per l'ambiente di un partecipante l'uso di un **container** (Incus o Docker), piuttosto che una sandbox generata da NsJail.
